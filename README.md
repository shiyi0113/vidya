# vidya

私人的认知工程项目。把各学科奠基的论文、演讲、笔记读透，提炼可复用的思维框架，打包成 Agent 能调用的 skill。

名字来自梵语 **vidyā**（विद्या）——不是一般意义的"知识"，是**直接看见**。反面 avidyā 不等于无知，而是看不清结构。这个项目对抗的就是 avidyā。

## 用意

一篇文章、一场演讲背后，沉淀着有人几十年的经验、思考，以及他消化过的别人的工作——这种密度的东西，是世上最稀缺的认知资产。

不限于一个学科。一个领域里看清的原理，常常蕴含着另一个领域尚未解开的问题的答案——原理的泛用性，最后往往超出它被提出时的想象。

让这种资产真正起作用，需要在你这边再做一次压缩。canon 是工作层——你跟原文打交道，把里面能反复使用的那一部分拎出来。skill 把它做成可调用的工具，在恰当情境下稳定触发判断。

skill 的具体形态由它自己长出来——有的可能就是一句判别，有的会演化成一整套协议。形态不预设。

## 两个部件

**canon 是工作层。** 你跟原文打交道、把里面能反复使用的那一部分拎出来的地方——一个区分、一条准则、一种重定向。形态不固定，可能是节选翻译、注释、或针对某段的标记；不替代原文，也不做整体评论。原文走外部链接（见后文：canon 与版权）。

**skills 是工具层。** 把 canon 里拎出来的东西操作化成 Agent 能调用的工具，让它在恰当情境下稳定触发判断。每个 skill 一个独立目录，`SKILL.md` 是单一事实来源；内部形态自由生长——可能是一句判别，也可能是一整套协议——对外暴露一组稳定字段（见后文：SKILL.md 接口）。

```
vidya/
├── canon/           # 跟原文打交道，把可反复使用的东西拎出来
└── skills/          # 把拎出来的东西做成 Agent 可调用的工具
    └── <skill-name>/
        ├── SKILL.md       # 单一事实来源
        ├── references/
        ├── scripts/
        └── assets/
```

## 受众

主要受众随文档类型而变：README 与 canon 写给未来的我；`SKILL.md` 写给加载 skill 的 Agent，因此是第二人称、命令式、可分支、可自检的形态。两类受众都不是陌生人——行文跳跃，术语不解释，判断不缓和。陌生人若路过：canon 是工作层，skills 是工具层，结构本身是机制；剩下的自己拼。

## 规则

每条都在抵消一种默认行为——没有它就会滑向某种失败模式。

**canon 做提取，不做整体评论。** 每条 entry 的产出是"我从这篇里拎出了什么可反复使用的东西"——一个区分、一条准则、一种重定向——加上必要的翻译与标记支撑；不是"这篇怎么样"。防的是把仓库写成书评——书评朝向作者，工作层朝向下游能调用的 skill。

**skill 必须有清晰的非对称性才入库。** 默认拒绝。门槛三条：核心非对称、触发情境、默认失败模式。说不清就留在 canon。防的是 skill 泛滥——80 个浅 skill 抵不上 8 个深的（完整判定见后文：skill 入库判定）。

**`SKILL.md` 是单一事实来源。** 一个 skill 的所有约定、触发条件、执行步骤都进 `SKILL.md`，不散落到 references 或脚注。防的是真相分裂——一分裂，维护就垮。

**不存平台相关的元数据。** 任何特定 Agent 框架的配置文件都不进核心仓库。防的是 vendor lock-in——skill 的生命周期应该比任何具体 Agent 平台都长。

## 不做什么

- **不做二手解读。** 不收博客对论文的转述、不收 listicle、不收"程序员必读的十本书"。
- **不做摘要。** 见上面规则一。
- **不预设 skill 形态。** 每个 skill 顺着原文自己的形态生长。Naur 的"理论建构"和 Lamport 的"happens-before"长出的 skill，结构上没理由相似。
- **不收藏式扩张。** canon 宁缺毋滥，skill 更严。

以下是操作层。往 canon 加新条目前扫一遍——规则不被实际遵守，是个人项目最讽刺的失败模式。

## skill 入库判定

候选 skill 必须能干净地回答下面五个问题。前四个答不齐就停，放回 canon 里继续养。

1. **它做的核心认知工作是什么？** 可能是一个区分（"A 不是 B"），可能是一种重定向（"你以为要 X，其实需要 Y"），可能是一组约束加身份（"在这种情境下不能做 Z"）。形态不限，工作内容必须能说清。说不出来就还没看清。
2. **它什么时候被需要？** 没有具体场景就没有 skill。
3. **不调用它时人会默认犯什么错？** 看不见反例，就证明自己也不会用。
4. **调用它后，产出的判断会有什么不同？** 说不清差异，就没有差异。
5. **能在两类以上情境中复用，或在单一情境中是关键判断吗？** 复用性不是 hard gate——Parnas 的 information hiding 只在切模块时触发，触发时无可替代。低频不等于浅。

## SKILL.md 接口

每个 skill 内部自由生长，对外必须暴露一组稳定字段：

- **Core work**：这个 skill 操作化了什么——一个区分、一种重定向、一组约束、一条准则，或其它能命名的形态。
- **When to use**：什么情境下必须调用。
- **Default failure mode**：不调用时人会用什么默认行为替代，那种替代为什么不够。
- **Procedure**：调用时执行什么——可能是一组检查的顺序，也可能是更复杂的协议骨架。
- **Output shape**：调用结束后产出的判断、状态或约束。

这五个是 `SKILL.md` 必须暴露的最小接口面，让外部（包括未来的我和 Agent）能稳定辨识 skill 在做什么。但它们不是 skill 的全部——skill 的内部内容（角色、约束、动作集、证据分类、压缩仪式等）自由生长，可能远超五字段所能描述。接口规定外部辨识，内部留给材料自己决定形态。

## 不入库的 skill 类型

反例比正例更能教未来的我做判断。看到自己在写其中之一，就停：

- **整篇论文的摘要包。** 没有核心非对称，只是复述。"Brooks《人月神话》总结"是读书笔记，不是 skill。
- **泛化建议合集。** "如何写出好代码"、"复杂系统设计原则"——解不开任何具体混淆，等于什么也没说。
- **没有触发条件的启发。** 比如"Naur 理论建构启发"——说不出什么时候被需要、不被需要时会怎样。
- **单一场景的小贴士。** 跨材料复用不了，单一情境里也不承担关键判断——是笔记，不是工具。
