# C 编程笔记

**Rob Pike · 1989年2月21日**

## 引言

Kernighan 与 Plauger 的 *The Elements of Programming Style* 是一本重要、影响也理所应得的书。但有时我觉得，书里那些精炼的规则被人当成了"良好风格的菜谱"，而非它们原本所要表达的——一种**哲学**的简练表达。如果书中说变量名应当被有意义地选取，那么是否就可推论出"以一篇关于其用途的小论文当变量名更好"？`MaximumValueUntilOverflow` 难道是比 `maxval` 更好的名字吗？我可不这么想。

下面是一组短小的随笔，它们合在一起鼓励的是**编程中以清晰为先**的哲学，而非给出硬性规则。我并不指望你同意每一条，因为这都是观点，而观点会随时间变化。但它们已经在我脑中（即使尚未落到纸上）积累很久了，并基于不少经验，所以我希望它们能帮助你思考如何**安排程序的细节**（关于如何安排整体设计的好文章我至今还没见过——这个课程在某种程度上正是要谈的）。如果你觉得它们很怪，没关系；如果你不同意，没关系；但若它们让你思考"为何不同意"，那就更好了。任何情况下你都不该因为我说要这么写就这么写；要按照你认为最能表达你想做之事的方式写程序，并**始终如一、毫不留情**地执行。

欢迎反馈。

## 排版问题

程序是一种"出版物"。它注定要被读——被作者、被另一个程序员（也许就是几天、几周、几年后的你自己）读，最后才被机器读。机器并不关心程序好不好看——能编译它就高兴；但人会关心，并且应当关心。有时人关心得过头了：**漂亮打印器**机械地产出"漂亮"输出，强调的是程序中无关紧要的细节——这就像把英语里的所有介词都加粗一样不智。尽管很多人觉得程序应该看起来像 Algol-68 报告（甚至有些系统强制你以那种风格编辑），一段清晰的程序并不会因这种排版变得更清晰，一段差程序则只显得更可笑。

一致地坚持排版约定对清晰呈现当然重要——缩进大概是最广为人知、也最有用的例子——但当**笔墨遮蔽了用意**时，排版便已喧宾夺主了。所以即便你只用普通老派打字机风格的输出，也要警惕排版上的滑稽。**避免装饰**——比如，注释要简短，没有横幅。把你想在程序里说的话清爽、一致地说出来，然后向前看。

## 变量名

啊，变量名。**长度并不是好名字的美德——表达上的清晰才是。** 一个全局变量若不常用，也许配得上一个长名，比如 `maxphysaddr`；而一个循环里每行都用的数组下标，没必要起得比 `i` 更花哨。把它叫 `index` 或 `elementnumber` 既要多打字（或多劳烦你的编辑器），又遮蔽了计算的细节。变量名一长，反而看不清在做什么。这部分是排版问题；比较：

```
for (i = 0 to 100)
    array[i] = 0
```

**对比**

```
for (elementnumber = 0 to 100)
    array[elementnumber] = 0;
```

随着真实例子变大，问题加速恶化。索引就是一种记号，把它当成记号就好。

指针也需要合理的记号。如果你一直坚持一种命名约定——`np` 容易被推出代表 "node pointer"——那么 `np` 与 `nodepointer` 一样易于记忆。下一节会进一步谈这个。

与可读编程的所有其他方面一样，**命名要前后一致**。如果你把一个变量叫 `maxphysaddr`，就别把它的"亲戚"叫 `lowestaddress`。

最后，我偏爱**最短长度但承载最大信息量**的名字，剩下的留给上下文去补全。例如全局变量在被使用时通常上下文很少，所以名字需要相对生动。因此对一个全局变量我会用 `maxphysaddr`（不是 `MaximumPhysicalAddress`），但对一个本地定义、本地使用的指针我用 `np` 而不是 `NodePointer`。这很大程度是品味问题，但品味与清晰相关。

我**不喜欢名字里嵌入大写字母**；在我这双偏文学的眼睛里，它们读起来不舒服。它们叮当作响，像差劲的排版。

## 指针的使用

C 的不寻常之处在于它允许指针指向一切。指针是锋利的工具——和所有锋利的工具一样，用得好可以非常富有成效，用得糟也会造成大破坏（写这篇前几天，我刚把一把木凿凿进了自己的拇指）。指针在学界声名不佳，被认为太危险、不知怎么就是"脏的"。但我认为它们是**有力的记号**，意思是它们能帮我们把意图说得清楚。

试想：当你拥有指向某对象的指针时，它就是**那个对象、且仅是那个对象**的名字。这听上去不值一提，可看看下面两个表达式：

```
np
node[i]
```

第一个指向一个节点；第二个（假设地）求值为同一个节点。但第二个是个**表达式**，它没那么简单。要解读它，我们必须知道 `node` 是什么、`i` 是什么、还要知道 `i` 与 `node` 之间的关联（多半未明文规定）由围绕着的程序的规则给出。**单看这个表达式本身，没有任何东西能保证 `i` 是 `node` 的合法下标，更别说它是否就是我们想要的那个元素。** 如果 `i`、`j`、`k` 都是 `node` 数组的下标，要写错就太容易了，编译器还帮不上忙。把这种东西传给子程序时尤其容易出错：指针是单一的事物；而"数组加下标"则要求接收子程序自觉地把它们视为一体。

一个**求值得到对象**的表达式，本质上比那个对象的**地址**更微妙、更易出错。正确使用指针可以简化代码：

```
parent->link[i].type
```

**对比**

```
lp->type.
```

如果我们要下一个元素的 type，那么是

```
parent->link[++i].type
```

或者

```
(++lp)->type.
```

`i` 在前进，但表达式的其余部分必须保持不变；用指针的话，要前进的只有一样东西。

排版考量也来了。用指针穿过结构比用表达式读起来更易：少用墨水，编译器和计算机也少做功。一个相关问题是，指针的类型决定了它如何被正确使用——这给了某些有益的编译期错误检查，而数组下标享受不到。此外，如果对象是结构体，其 tag 字段就提醒着其类型，因此

```
np->left
```

已足够生动；若是数组下标，数组就会有一个精挑细选的名字，表达式最终会更长：

```
node[i].left.
```

例子越大，这些多出来的字符就越令人厌烦。

有一条经验：如果你看到代码里有许多相似而复杂的表达式都求值为某个数据结构的元素，那么**审慎使用指针**通常能把代码理顺。试想

```c
if (goleft)
    p->left = p->right->left;
else
    p->right = p->left->right;
```

要是把 `p` 替换成一个复合表达式会变成什么样？有时引入一个临时变量（这里是 `p`）或一个宏来"提炼"计算是值得的。

## 过程名

**过程名应反映它做什么；函数名应反映它返回什么**。函数被用在表达式中——尤其是 `if` 之类——所以读起来必须合适。

```
if (checksize(x))
```

帮不上忙，因为我们无法判断 `checksize` 在错误时返回真还是非错误时返回真。换成

```
if (validsize(x))
```

意思立刻清楚，将来误用这个例程的可能性也降低了。

## 注释

这是个微妙之事，需要品味与判断。我倾向**少注释**而非多。原因有几条：第一，如果代码清晰、用了好的类型名和变量名，它应当能"自我说明"。第二，注释**不会被编译器检查**，所以并不能保证它正确——尤其在代码被修改之后。一条误导性的注释会让人非常困惑。第三，是排版问题：注释把代码搅乱了。

但我有时候也会写注释。**几乎只用作"对接下来内容的导言"**。例如：解释全局变量与类型的用途（这是大型程序中我**总是**会注释的一件事）；作为对一个特殊或关键过程的导引；或为大段计算分段。

有种臭名昭著的注释风格：

```c
i = i + 1;     /* Add one to i */
```

还有更糟的写法：

```c
/**********************************
 *                                *
 *        Add one to i            *
 *                                *
 **********************************/

i = i + 1;
```

现在不要笑——等你在真实代码里看到再笑。

避免注释里的"花哨排版"，避免大块注释——也许只在关键段（如核心数据结构的声明）之前可以；通常**对数据的注释比对算法的注释更有用**。基本上：避免注释。如果你的代码需要注释才能被理解，那就**重写它**，让它更易理解。这就引出下一节——

## 复杂性

绝大多数程序都太复杂——意思是，比"为有效解决其问题"所需的复杂度更复杂。为什么？多半是糟糕的设计造成的，但那是个大题目，这里我跳过。然而程序也常在**微观层面**变复杂，这是我可以在此处理的。

**规则 1。** 你猜不准程序会把时间花在哪里。瓶颈出现在意想不到的地方，所以**别二次猜测**——在你证明那才是瓶颈之前，不要塞进什么"加速小技巧"。

**规则 2。** **测量。** 在测量之前别为速度调优；即便测量过了，也只在某一段代码**远远**压过其他时再去调。

**规则 3。** 花哨的算法在 `n` 小时反而慢，而 `n` 通常就是小。花哨算法常数项大。在你**确定** `n` 经常会变得很大之前，别耍花活。（即使 `n` 真的会变大，先去用规则 2。）例如，对于日常问题，**二叉树永远比 splay 树快**。

**规则 4。** 花哨算法 bug 多于简单算法，并且实现起来困难得多。**用简单算法、用简单数据结构。**

下面这些数据结构对几乎所有实用程序而言都是一个**完整清单**：

- 数组（array）
- 链表（linked list）
- 哈希表（hash table）
- 二叉树（binary tree）

当然，你也必须准备把它们组合成复合数据结构。比如，一张符号表可以实现为"哈希表里装着一串链表，链表的元素是字符数组"。

**规则 5。** **数据为王。** 如果你选对了数据结构、把事情组织得当，**算法几乎都是显而易见的**。数据结构而非算法才是编程的中心。（参见 Brooks 第 102 页。）

**规则 6。** 没有规则 6。

## 用数据来编程

算法或算法的细节常常可以**作为数据**——而不是大量的 `if` 语句——更紧凑、更高效、更具表达力地编码出来。原因在于：手头任务的复杂性，如果是由若干**相互独立的细节**组合而来的，就**可以被编码**。一个经典例子是**解析表**——把一门编程语言的文法编码成一种可以被一段固定、相当简单的代码所解释的形式。**有限状态机**特别适合用这种方式攻击；几乎任何把某种抽象输入"解析"为一系列独立"动作"的程序，都可以受益地构造为**数据驱动的算法**。

这种设计或许最有趣的一面是：表本身有时可以**由另一个程序生成**——经典案例是**解析器生成器**。再举个更接地气的例子：如果一个操作系统由"把 I/O 请求关联到对应设备驱动"的一组表来驱动，那么系统就可以由读取"特定机器上挂了哪些设备"描述并打印对应表的程序来"配置"。

数据驱动程序在初学者中不常见的一个原因，是**Pascal 的暴政**。Pascal——一如其创造者——坚信代码与数据的分离。因此（至少在其原始形式中）它没有创建初始化数据的能力。这与图灵和冯·诺依曼的理论背道而驰——而那两条正是"存储程序计算机"的基本原理。**代码与数据是同一回事**，至少**可以是**。否则你怎么解释编译器是怎么工作的？（函数式语言对 I/O 也有类似毛病。）

## 函数指针

Pascal 暴政的另一个后果是初学者不用函数指针。（Pascal 里没有"以函数为值"的变量。）用函数指针来编码复杂性，有些有趣的性质。

**一部分复杂性被传递给了被指向的例程。** 那个例程必须遵守某个标准协议——它是同一组以相同方式被调用的例程之一——但除此之外，它做什么是它自己的事。复杂性被**分布**了。

这里有"协议"的思想：所有以相同方式使用的函数必须以相同方式行事。这便于文档、测试、扩展，乃至让程序在网络上分布运行——协议可以编码为远程过程调用（RPC）。

我主张：**函数指针的清晰使用，是面向对象编程的核心**。给定一组你希望对数据执行的操作，以及一组你希望响应这些操作的数据类型，把程序拼起来的最简单方法，就是**为每种类型准备一组函数指针**。一言以蔽之，这就定义了类与方法。OO 语言当然给你更多——更漂亮的语法、派生类型等等——但概念上它们提供的并不太多。

把数据驱动程序与函数指针结合起来，会带来一种惊人富有表达力的工作方式。在我的经验里，它常常带来令人愉快的惊喜。即便没有专门的 OO 语言，**你也能不费额外之力获得 90% 的好处**，并对结果有更多掌控。我极力推荐这种实现风格。所有我以这种方式组织的程序，在大量演化之后都活得很舒服——比那些不那么有纪律的方法好得多。也许就是这点：**它强加的纪律在长期上回报丰厚**。

## include 文件

简单规则：**include 文件不应再 include 其他 include 文件**。如果它们以注释（或隐含地）说明需要哪些文件先被包含，那么"决定要包哪些"这件事就被推回给用户（程序员），但**以一种容易处理的方式**进行——并且，从构造上避免了多次包含。多次包含是系统编程中的灾祸：要编译一个 C 源文件，某些文件被包含五次乃至更多并不罕见。Unix 的 `/usr/include/sys` 在这方面糟糕透顶。

有种小把戏使用 `#ifdef` 来防止文件被读两次，但实践中常常用错——`#ifdef` 写在文件**自己**里，而不是写在**包含它**的文件里。结果是成千上万行无谓的代码穿过词法分析器（在好的编译器里这是开销最大的阶段）。

照那条简单规则做就行了。
