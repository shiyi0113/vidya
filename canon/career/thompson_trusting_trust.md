# 对"信任"的反思

**图灵奖演讲 · Ken Thompson · 1984年8月**

> 一个声称程序中没有特洛伊木马的陈述，能让人信任到何种程度？也许更重要的是，去信任那些写了这些软件的人。

## 引言

感谢 ACM 颁给我这个奖。我不禁觉得自己之所以获此荣誉，靠的是时机和运气，不亚于技术贡献。UNIX 因整个产业从中央大型机向独立小型机转变而风行起来。我猜想，要不是 Daniel Bobrow [1] 当年没钱用 PDP-10、不得不"将就"用 PDP-11，今天站在这里的就该是他。何况，今天 UNIX 的状态是大量人员劳动的结果。

有句老话说："请你来跳舞的那个人，你就该陪她跳到底。"——意思是我应该谈 UNIX。我多年没有从事 UNIX 主线工作，却一直因别人的工作而获得了不应得的赞誉。所以我不打算谈 UNIX，但我要感谢所有做出贡献的人。

这就让我想到 Dennis Ritchie。我们的合作是一种美的存在。共事十年，我只能想起一次工作上的失调——那一次我发现，我们俩各自写了同一段 20 行的汇编程序。我比对了源代码，惊讶地发现它们逐字符一致。我们合作的成果远远大于各自单独贡献的总和。

我是个程序员。在 1040 表上，我写的职业就是这个。作为程序员，我写程序。我想给大家展示我所写过的最可爱的一段程序。我会分三阶段来讲，最后把它们串到一起。

## 第一阶段

在大学里，那时还没有电子游戏，我们靠出编程题自娱自乐。其中一个最受欢迎的题目是：写一个最短的"自我复制"程序。既然这是个脱离实际的练习，惯用的语言是 FORTRAN。其实选 FORTRAN 是出于和"三脚同跑"游戏一样的理由。

更精确地说，问题是：写一段源程序，编译并执行后输出与源代码完全相同的副本。如果你从未做过，我建议你自己动手试试。发现"怎么做"本身是一种启示，远胜于被告知"怎么做"所获得的好处。"最短"那条只是个激励，便于显出技艺、决出胜负。

图 1 展示了一个用 C 编程语言写成的自我复制程序。（吹毛求疵的人会指出，这并不严格是一个"自我复制程序"，但它会产出一个自我复制程序。）这条参赛作品过大，无法获奖，但它演示了技巧，并具备我接下来叙事所需的两个重要性质：（1）这个程序很容易由另一个程序写出来；（2）这个程序可以包含任意多的"额外行李"，这些行李会与主算法一同被复制。在这个例子里，连注释都被一并复制了。

```c
char s[] = {
    '\t',
    '0',
    '\n',
    '}',
    ';',
    '\n',
    '\n',
    '/',
    '*',
    '\n',
    (213 lines deleted)
    0
};

/*
 * The string s is a
 * representation of the body
 * of this program from '0'
 * to the end.
 */

main()
{
    int i;

    printf("char\ts[] = {\n");
    for(i = 0; s[i]; i++)
        printf("\t%d,\n", s[i]);
    printf("%s", s);
}
```

| `"xxx"` | 多字符字符串 |

| `%s` | 转换为字符串的格式 |

## 第二阶段

C 编译器本身是用 C 写的。我接下来要讲的，是当编译器用其自身语言来写时所产生的众多"先有鸡还是先有蛋"问题中的一个。我会用 C 编译器中的一个具体例子。

C 允许用字符串构造来初始化字符数组。字符串中的单个字符可以用转义序列表示不可打印字符。例如：

```
"Hello world\n"
```

代表一段含有"\n"的字符串，"\n"代表换行符。

图 2.1 是 C 编译器中用于解释字符转义序列的代码的理想化形式。这是一段奇妙的代码：它以完全可移植的方式"知道"在任意字符集中，新行被编码成什么。这种"知道"使它得以重新编译自己，从而把这种知识永久延续下去。

```c
c = next();
if(c != '\\')
    return(c);
c = next();
if(c == '\\')
    return('\\');
if(c == 'n')
    return('\n');
```

**图 2.1.**

假设我们想扩展 C 编译器，让它支持序列 "\v" 表示垂直制表符。对图 2.1 的扩展很显然，呈现在图 2.2 中。我们重新编译 C 编译器，但得到一个错误。显然，因为编译器的二进制版本并不知道 "\v"，所以源代码不是合法的 C。我们必须"训练"这个编译器。在它"知道""\v"的含义之后，新加入的改动才会变成合法的 C。我们查 ASCII 表，垂直制表符的十进制值是 11。我们把源码改成图 2.3 的样子。这下，旧编译器就接受新源码了。我们把得到的二进制安装为新的官方 C 编译器，从此就可以用图 2.2 那种可移植的写法了。

```c
c = next();
if(c != '\\')
    return(c);
c = next();
if(c == '\\')
    return('\\');
if(c == 'n')
    return('\n');
if(c == 'v')
    return('\v');
```

**图 2.2.**

```c
c = next();
if(c != '\\')
    return(c);
c = next();
if(c == '\\')
    return('\\');
if(c == 'n')
    return('\n');
if(c == 'v')
    return(11);
```

**图 2.3.**

这是个深刻的概念。这是我所见过的最接近"会学习"的程序：只需告诉它一次，从此便可使用这个自我引用的定义。

## 第三阶段

回到 C 编译器，图 3.1 表示 C 编译器中的高层控制部分，其中名为 `compile` 的例程被调用以编译下一行源码。图 3.2 展示了对编译器的一个简单修改，每当匹配到某种特定模式时，就故意误编译源码。如果这不是有意为之，它就叫"编译器 bug"；既然是有意为之，它就该叫"特洛伊木马"。

我植入编译器的真实 bug 会匹配 UNIX "login" 命令中的代码。替换后的代码会误编译 login 命令，使它既能接受原本的加密密码，也能接受某个特定的已知密码。这样，只要这段代码以二进制形式安装、并被用于编译 login 命令，我就能以任意用户身份登录该系统。

如此明目张胆的代码很快就会被发现。哪怕只是漫不经心地翻一翻 C 编译器的源代码，也会引起怀疑。

最后一步呈现在图 3.3 中。它在已有的特洛伊木马之上再加上第二个木马。这第二个模式针对的是 C 编译器本身。替换代码是一段第一阶段那样的自我复制程序，它会把这两个特洛伊木马都插回到编译器中。这要像第二阶段那样有个"学习阶段"。我们先用正常的 C 编译器编译这份被修改过的源码，得到一个被植入木马的二进制。把这个二进制安装为官方的 C。现在我们可以把编译器源码里的 bug 删掉，新二进制每次编译时都会把 bug 重新插回去。当然，login 命令会一直带着这个 bug，而源码中却到处都找不到痕迹。

```c
compile(s)
char *s;
{
    ...
}
```

## 寓意

寓意是显然的：你不能信任不是你完全自己写出来的代码。（特别是来自雇用了像我这样的人的公司的代码。）任何源码层面的核查或审视都无法保护你免受不可信代码的危害。在演示这种攻击的可能性时，我挑了 C 编译器开刀。我本可以挑任何处理程序的程序——汇编器、加载器，乃至硬件微代码。程序所在的层次越低，这类 bug 就越难被察觉。一个安装得当的微代码 bug 几乎无法检测。

在试图说服你"我不可信"之后，我想做一些道德上的告诫。我想批评新闻界对所谓"黑客"——414 帮、Dalton 帮等等——的处理方式。这些孩子的所作所为，往最好里说是破坏行为，往最坏里说大概要算闯入和盗窃。是刑事法规的不完善，才让黑客们免于严肃起诉。容易遭受这类活动侵害的公司（绝大多数大公司都极其脆弱）正在大力推动刑法的更新。在少数州里，未经授权访问计算机系统已属重罪；在更多的州、乃至联邦国会，这件事正在被着手处理。

一种危险的形势正在酝酿：一方面，报纸、电视和电影把这些破坏者捧成"神童"；另一方面，他们的所作所为不久就会让人身陷囹圄多年。

我看过这些孩子在国会作证。很显然，他们对自己行为的严重性毫无自觉。这中间显然有一道文化鸿沟。闯入计算机系统应当与闯入邻居家一样受到社会的谴责。邻居家门没锁，不应改变这种行为的性质。新闻界必须明白：错用计算机并不比酒后驾车更值得赞叹。
