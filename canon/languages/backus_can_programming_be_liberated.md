## 摘要

**常规程序设计语言越来越庞大，却没有变得更强**。其最基础层级上的内禀缺陷使它们既肥又弱：**继承自共同祖先——冯·诺依曼计算机——的"逐字编程"原始风格**；语义与状态转换的紧密耦合；把编程切成"表达式世界"与"语句世界"；**无能有效地使用强力的"组合形式"（combining forms）从已有程序构建新程序**；以及**缺乏用以推理程序的有用数学性质**。

一种**函数式编程风格**则建立在用"组合形式"构造程序之上。**函数式程序处理结构化数据，常常无须重复或递归，分层构造，不为参数命名，不需要复杂的过程声明机制即可普遍适用**。组合形式可以用高层程序去构造更高层程序——**这种风格在传统语言中无法实现**。

伴随函数式风格的还有一种**"程序代数"**——其中变量在程序之上取值、运算是组合形式。该代数可被用以变换程序、并求解"未知数为程序"的方程——很像高中代数中变换方程那样。这些变换由代数律给出，并在写程序的同一种语言中执行。**组合形式的选取不仅看其编程力，也看其相应代数律的力**。代数的一般性定理给出大量程序的详细行为与终止条件。

**新一类计算系统在编程语言与状态转换规则两面都使用函数式风格**。**与冯·诺依曼语言不同——这些系统的语义与状态弱耦合**——**每一次重要计算只发生一次状态转换**。

**关键词**：函数式编程、程序代数、组合形式、函数式形式、编程语言、冯·诺依曼计算机、冯·诺依曼语言、计算系统模型、应用式（applicative）计算系统、应用式状态转换系统、程序变换、程序正确性、程序终止、metacomposition

## 1. 常规程序设计语言：又肥又松

**程序设计语言看上去陷入了麻烦**。每一种新语言把前作的所有特性（略加清理）连同更多新加项一并纳入。某些语言的手册超过 500 页；另一些靠密集形式主义把复杂描述压进较短手册。美国国防部当下计划要做一种委员会设计的语言标准——**手册可能长达 1000 页**。每种新语言宣称有新而时髦的特性（强类型、结构化控制语句之类）——但**坦白说，几乎没有哪种语言把"编程"做得更便宜或更可靠到能够正名其制造与学习成本**。

由于规模的大幅增加只带来力的小幅提升——**Pascal 这种较小、较优雅的语言仍然受欢迎**。但**对一种能帮助我们思考程序的强方法学的渴求是迫切的**——而**没有一种常规语言能哪怕开始满足这种需要**。事实上**常规语言制造了我们对"程序"思考方式上的不必要的混乱**。

二十年来，程序设计语言一路走向当下的肥胖——**结果是研究与发明语言之事大失其原本的兴奋**。这一领域如今属于那些"宁愿与厚厚的细节合编共事、也不愿与新思想搏斗"的人。**关于程序设计语言的讨论，常常更像中世纪关于"针尖上能跳几个天使"的辩论，而不是不同基本概念之间令人激动的较量**。

许多有创造力的计算机科学家**已从"发明语言"撤到"发明描述语言的工具"上**。可惜他们大多满足于把这些优雅工具用来研究既有语言上的"疣与痣"。**当 Dana Scott 的优雅工具被用来审视常规语言那骇人的类型结构后**——令人意外的是，**这么多人居然仍消极地接受那种结构，而不是积极搜索新结构**。

**本文目的有二**：第一，提示**常规语言框架中根本性的缺陷使其表达力孱弱与癌性增长成为必然**；第二，提示一些通向**新种类语言设计**的探索路径。

## 2. 计算系统的模型

每一种程序设计语言之下都有一种**它所控制的计算系统模型**。有些模型是纯抽象，有些由硬件呈现，有些由编译/解释程序呈现。在更细审视常规语言之前，先简略调查现有模型——以作进入"可行替代品"之前的引子。

### 2.1 模型的判据

**2.1.1 基础**：模型是否有优雅简洁的数学描述？这描述对证明模型行为的有用事实是否有用？还是模型复杂到其描述既臃肿又对数学没什么用？

**2.1.2 历史敏感性**：模型是否含"存储"概念，使得一段程序能保存可影响后程序行为的信息？也就是说，模型是否对历史敏感？

**2.1.3 语义类型**：程序是否在状态间相继转换（状态非程序），直到达终态（**状态转换语义**）？状态简单还是复杂？还是说"程序"可被相继归约为更简单的"程序"，最终得到一个"范式程序"——即结果（**归约语义**）？

**2.1.4 程序的清晰性与概念有用性**：模型的程序是否对过程或计算有清晰表达？它们是否包含能帮我们形式化与推理过程的概念？

### 2.2 模型分类

按上述判据，可将计算系统模型粗分三类：**简单操作模型、应用式模型、冯·诺依曼模型**。

**2.2.1 简单操作模型**（如图灵机、各种自动机）：**基础**简洁有用；**历史敏感**，有存储；**语义**为非常简单状态间的状态转换；**程序清晰性**：程序晦涩、概念上无助。

**2.2.2 应用式模型**（如 Church 的 λ 演算 [5]、Curry 的组合子系统 [6]、纯 LISP [17]、本文将描述的函数式编程系统）：**基础**简洁有用；**无存储、对历史不敏感**；**归约语义、无状态**；**程序可清晰且概念上有助**。

**2.2.3 冯·诺依曼模型**（如冯·诺依曼计算机、常规程序设计语言）：**基础**复杂、臃肿、不有用；**历史敏感、有存储**；**复杂状态间的状态转换语义**；**程序在概念上不那么有助**——清晰性中等。

上述分类承认是粗糙且可争议的。例如 Arvind 与 Gostelow [1]、Dennis [7]、Kosinski [13] 等人发展的**数据流语言**部分像简单操作模型，但其程序更清晰；也许可主张其中某些具有归约语义。**总之这一分类只是一张待讨论领地的粗略地图**——下文将只谈应用式与冯·诺依曼模型。

## 3. 冯·诺依曼计算机

要理解常规程序设计语言的问题，必先审视其**智识父母——冯·诺依曼计算机**。**何为冯·诺依曼计算机？** 三十多年前冯·诺依曼及其他人构思它时——它是一种简化了一系列工程与编程问题的优雅、实用、统一思想。**虽然产生它的条件已彻底改变——我们仍然把"计算机"概念等同于这一三十年前的概念**。

最简形式下，冯·诺依曼计算机有三部分：**CPU、存储、以及一条能在 CPU 与存储之间传单字（并向存储发地址）的连接管道**——**我建议把这条管道叫"冯·诺依曼瓶颈"**。**程序的任务是以某种重大方式改变存储内容**——一旦想到这必须**完全靠在 CPU 与存储间来回泵单字**完成——这名字的由来就清楚了。

讽刺的是，这条瓶颈中**很大一部分流量并非有用数据，而仅仅是数据的名字、用以计算这些名字的运算与数据**。一字被送过去之前其地址必须在 CPU 中——**所以地址要么从存储经管道送来、要么由某条 CPU 操作产生**——若由存储送来，那地址的地址又要么由存储送来、要么由 CPU 产生……如此往复。

**做巨大改变给存储——一定有比通过冯·诺依曼瓶颈推送大量字更不原始的方式**。这条管道不仅是问题数据流量的字面瓶颈——**更重要的是**：**它是把我们绑死在"逐字思考"上的智识瓶颈，而不是鼓励我们以手头任务更大的概念单元来思考**。**所以编程基本上就是规划与细化这巨量字流过冯·诺依曼瓶颈的来回流量——而其中很大部分流量与有效数据无关，只是"在哪里取它"**。

## 4. 冯·诺依曼语言

常规程序设计语言基本上是**冯·诺依曼计算机的高级、复杂版本**。我们三十年来"只有一种计算机"的信念，是我们"只有一种程序设计语言——常规即冯·诺依曼语言"信念的基础。Fortran 与 Algol 68 之间的差异虽然不少——**但"两者都基于冯·诺依曼计算机的编程风格"这件事远比这些差异更显著**。我把常规语言称作"冯·诺依曼语言"以纪念其源流与风格——**并不是把它们的复杂归咎于那位伟大的数学家**——事实上**也许该说我自己对此问题负有些责任**。

冯·诺依曼语言**用变量模仿计算机的存储格；用控制语句细化它的跳转与测试指令；用赋值语句模仿它的取存与算术**。**赋值语句正是程序设计语言的"冯·诺依曼瓶颈"**——它使我们仍以"逐字"方式思考，正如计算机瓶颈所做的。

考虑一段典型程序：**其中心是一组带下标变量的赋值语句**。每条赋值产生一字结果——**程序必须让这些语句被执行许多次（同时改下标值），以让存储发生整体上的所求改变——因为只能逐字做**。**程序员于是关心赋值瓶颈中字的流动，并据此设计嵌套的控制语句以引发必要重复**。

更糟的是，**赋值语句把编程切成两个世界**：**第一个世界**是赋值的右侧——一个有用代数性质的、有序的"表达式世界"（虽然这些性质常被副作用毁掉）——**这是大多数有用计算发生的世界**。**第二个世界**是"语句世界"——其中主语句正是赋值本身——其余语句之所以存在，**只是为了使基于这一原始构造（赋值）的计算成为可能**。**这是个杂乱、几无有用数学性质的世界**——**结构化编程可视为对这一混沌世界引入一些秩序的微小努力——但它对"逐字、原始用循环/下标/分支的冯·诺依曼风格所造的根本问题"几乎未能进攻**。

**我们对冯·诺依曼语言的执着延续了冯·诺依曼计算机的优势地位**——**对它的依赖让"非冯·诺依曼语言"在经济上不划算并限制了它们的发展**。**由于没有以"非冯·诺依曼原理"为基的全规模、有效编程风格——新计算机体系结构便失去了智识地基**（参见 §15）。

应用式计算系统**缺存储与历史敏感性**——这是它们没能为计算机设计提供基础的根本原因。再者——大多数应用式系统把 λ 演算的"代换运算"作其基本运算——**这种运算几乎力量无限——但其完整高效实现给机器设计者带来巨大困难**。再加之，为了引入存储并提升其在冯·诺依曼计算机上的效率——**应用式系统往往被一个庞大冯·诺依曼系统所吞没**——例如纯 LISP 常被埋在带有许多冯·诺依曼特性的庞大扩展里。所得复杂系统对机器设计者**几乎没什么指导**。

## 5. 冯·诺依曼程序与函数式程序的对比

要更细致看冯·诺依曼语言的缺陷——**比较一个常规的内积程序与一个用某简单语言写就的函数式版本**——后者在下文进一步定义。

### 5.1 内积的冯·诺依曼程序

```
c := 0
for i := 1 step 1 until n do
    c := c + a[i] × b[i]
```

值得注意的几点：

a) 它的语句**按复杂规则在不可见的"状态"上运行**。
b) **它不分层**——除赋值的右边外，它不从更简单的实体构造复杂实体（**更大程序通常会**）。
c) **它动态而重复**——必须**在脑里执行**才能理解。
d) 它通过赋值的重复与变量 i 的修改来"逐字计算"。
e) 数据的一部分（n）**写在程序里**——因此不普适，只对长度 n 的向量奏效。
f) **它给参数命名**——只能用于向量 a 与 b——要变得通用，需要**过程声明**（涉及调用法等复杂议题）。
g) 它的"管家"运算（housekeeping）由**散布各处的符号表示**（在 for 与下标里）——**使得"把管家运算合并为单个、强力、广用的算子"成为不可能**——因此每次都要从头开始写 `for i ← …`、`for j ← …` 后跟撒着 i、j 的赋值。

### 5.2 内积的函数式程序

```
Def Innerproduct ≡ (Insert +) o (ApplyToAll ×) o Transpose
或简写：
Def IP ≡ (/+) o (α×) o Trans.
```

`Composition (o)`、`Insert (/)`、`ApplyToAll (α)` 是**函数式形式**——它们把已有函数组合为新函数。`f o g` 是"先 g 后 f"的复合；`αf` 是把 f 应用到参数每一成员所得函数。把"f 应用于对象 x"的结果记为 `f:x`——则 `Innerproduct` 应用于对向量 `<<1,2,3>, <6,5,4>>` 的求值步骤如下：

```
IP : <<1,2,3>, <6,5,4>>
= 由 IP 定义               (/+) o (α×) o Trans : <<1,2,3>, <6,5,4>>
= 复合 o 的效果             (/+) : ((α×) : (Trans : <<1,2,3>, <6,5,4>>))
= 应用 Transpose            (/+) : ((α×) : <<1,6>, <2,5>, <3,4>>)
= ApplyToAll, α 的效果      (/+) : <× : <1,6>, × : <2,5>, × : <3,4>>
= 应用 ×                    (/+) : <6, 10, 12>
= Insert, / 的效果          + : <6, + : <10, 12>>
= 应用 +                    + : <6, 22>
= 再次应用 +                 28
```

将其性质与冯·诺依曼版本比较：

a) **它只对参数运行**——**没有隐藏状态或复杂转换规则**——**只有两种规则**：把函数应用于其参数；与，由"函数式形式（如 `f o g`、`α f`）"在已知 f, g（形式参数）时获得其所表函数。
b) **分层**：由三个更简单函数（`+`、`×`、`Trans`）与三种函数式形式（`f o g`、`α f`、`/ f`）造出。
c) **静态、无重复**——结构本身就有助理解，不需脑里执行。例如知 `f o g`、`α f`、`× / Trans` 的效果——便可知 `α ×` 与 `(α ×) o Trans` 的效果，等等。
d) **整概念单元**地运行（不是字）——3 步——无步骤被重复。
e) **不嵌入数据**——完全通用——对任何相容的向量对都奏效。
f) **不命名参数**——**无须过程声明或复杂代换规则**。
g) 使用了**许多其他程序里也通用**的"管家形式与函数"——其实只有 `+` 与 `×` 不是关于管家的——**这些形式与函数能与别的组合，造更高层的管家算子**。

§14 勾勒一种系统——**意在让上述函数式风格于一个"历史敏感、框架简单"的系统里可用**——但要让这种应用式风格成为优雅且实用语言之基，仍有大量工作。**就当下而言，上述对比已显露冯·诺依曼语言的若干严重缺陷，并可作为追问其当前肥胖状态成因的起点**。

## 6. 语言"框架"与"可换部件"

把程序设计语言分两部分：**框架**（系统总体规则）；**可换部件**（其存在被框架所预期，但其具体行为不由框架规定）。例如 Algol 的 `for` 语句与几乎所有其他语句属框架——库函数与用户自定义过程是可换部件。**一种语言的框架描述其固定特性，并为其可换特性提供普适环境**。

设有一种语言——**有一个小框架，能把多种强力特性都作为可换部件容纳进来**——这框架便能支持许多不同特性与风格而本身不必更改。**与此愉快可能性相反——冯·诺依曼语言总有一个庞大框架与极有限的可换部件**。**何以如此？** 答案涉及冯·诺依曼语言的两大问题。

**第一问题**源于冯·诺依曼"逐字编程"的风格——**它要求字与状态来回流动，正如经过冯·诺依曼瓶颈**。所以**冯·诺依曼语言必须有与状态紧耦合的语义——计算的每一细节都改变状态**——**结果是每一特性的每一细节都必须被建进"状态"及其转换规则中**。**所以冯·诺依曼语言的每一特性都必须在框架里被以令人麻木的细节铺开——并且——许多复杂特性是为了支撑那基本上孱弱的'逐字风格'而需要的——结果是冯·诺依曼语言必然庞大刚硬的框架**。

## 7. 可换部件与组合形式

**第二问题**：冯·诺依曼语言的可换部件**表达力极少**。它们巨大的体型雄辩地证明这一点——**毕竟，若设计者知道现在被他建进框架的所有这些复杂特性日后能作为可换部件加进来，他就不会那么急着把它们建进框架**。

**也许提供强大可换部件最重要的一项——是可被普遍地用以"由旧过程造新过程"的组合形式**。**冯·诺依曼语言只提供原始的组合形式——并且其框架对它们的充分使用造成阻碍**。

阻碍之一是冯·诺依曼语言中**"表达式世界"与"语句世界"的分裂**——函数式形式天然属表达式世界——但**无论它们多强**，**只能造产生一字结果的表达式**——而要把这些一字结果合成整体结果，**必须在"语句世界"中**——**单字组合不该是我们真正应思考的事——但这正是用冯·诺依曼语言编任何任务时大量的工作**。语句世界为帮助"由单字组装总体结果"提供了一些原始组合形式——`for`、`while`、`if-then-else`——**但两个世界的分裂使任一世界中的组合形式都无法获得"未分裂世界中能达到"的全部力量**。

阻碍之二是冯·诺依曼语言**精巧的命名约定**——又被调用过程时所需的**代换规则**进一步复杂化。**每一种都要在框架里建立复杂机制**——使变量、带下标变量、指针、文件名、过程名、按值/按名形参等等都能被恰当解释。**所有这些命名、约定、规则都妨碍简单组合形式的使用**。

## 8. APL 与逐字编程

既然我已多说了"逐字编程"——必须谈谈 APL [12]。**Iverson 让我们看到了"既不逐字也不依赖 λ 表达式"的程序，并把新种类的函数式形式引入了我们**——我们对此应有大恩。又因 APL 的赋值语句可以存数组——**其函数式形式的效果被延伸到单条赋值之外**。

但 APL 仍**把编程切成"表达式世界与语句世界"**——把程序写成"一行式"的努力——部分是出于"想呆在更有序的表达式世界里"。APL 恰好有三种函数式形式（**inner product / outer product / reduction**）——它们时而难用、数量不够，且其使用被限于表达式世界。

此外，**APL 的语义仍然太紧地耦合于状态**——结果——尽管语言简洁有力——其框架仍具有冯·诺依曼语言典型的复杂与僵硬。

## 9. 冯·诺依曼语言缺乏有用的数学性质

至此我们谈了冯·诺依曼语言的总体规模与不灵活——**另一重要缺陷是其缺乏推理程序所需的有用数学性质，以及它们对程序推理造成的障碍**。尽管已发表了大量关于"程序事实证明"的卓越工作——**冯·诺依曼语言几乎没有有助于此方向的性质，却有许多障碍（如副作用、混叠）**。

**Denotational 语义** [23] 及其基础 [20, 21] 给出关于程序里隐含的"域与函数空间"的极有用数学理解——应用于应用式语言（如 [16] 中"递归程序"）时，**其基础给出强力工具**——既描述语言又证明程序性质。**应用于冯·诺依曼语言时——它给出精确语义描述并有助于识别问题点**——但**语言的复杂在描述里被镜像**——成了一大堆产生式、域、函数与方程——比起语言参考手册仅略多一点助证程序事实之力（仅因更不歧义）。

**公理语义** [11] 把冯·诺依曼程序不优雅的性质（即"对状态的变换"）精确地重述为"对谓词的变换"——**那"逐字、重复"的游戏并未改变，只是换了场地**——**对冯·诺依曼程序证明事实的公理化游戏复杂之至——这让其实践者的成功更值钦佩**。其成功除了他们巧思之外还基于两点：**第一**——游戏被限定在冯·诺依曼语言"小而弱的子集"上（其状态远比真实者简单）；**第二**——新场地（谓词及其变换）比旧场地（状态及其变换）更丰富、更有序、更有效——**但限制游戏并把它转移到更有效领域并不能让它处理真实程序（含必要的过程调用与混叠复杂），也不能消去基本冯·诺依曼风格的笨拙性**——当公理语义被扩展以覆盖典型冯·诺依曼语言之更多内容时，**其有效性随所需复杂度的增加而开始下降**。

**Denotational 语义与公理语义都是描述性形式主义——其基础体现了优雅而有力的概念**——但**用它们去描述一种冯·诺依曼语言，并不能产出一种优雅有力的语言——正如用优雅的现代机器去造一辆 Edsel 也不能造出一辆优雅现代的车**。

无论如何，**关于程序的证明所用的语言是逻辑语言，不是程序设计语言**——**证明谈论程序，但不能直接涉及程序——因为冯·诺依曼语言的公理太不可用**。**与此相反——许多普通证明是用代数方法导出的**——这些方法要求语言具备某些代数性质——这样代数律就能以相当机械的方式把问题变成解。例如解方程

```
ax + bx = a + b（设 a + b ≠ 0）
```

依次机械地施以分配律、单位元、消去律：

```
(a + b)x = a + b
(a + b)x = (a + b)·1
x = 1
```

**于是我们没有离开"代数"这门"语言"就证明了 x = 1**。**冯·诺依曼语言的怪诞语法很少给我们这种"变换程序"的可能**——稍后会看到，**程序可以以一种带有相伴代数的语言来表达**——这种代数可被用来变换程序、解"未知数为程序"的方程——很像高中代数那样。**代数变换与证明使用的就是程序自身的语言，而不是"谈论程序的逻辑语言"**。

## 10. 冯·诺依曼语言的替代是什么？

讨论替代之前——**我对上面这种否定且不太精确的讨论感到遗憾**——但我们大多数人对这些庞大孱弱语言的安然接受让我久已不安。我之所以困扰，是**因为这种接受将本可用于探寻新结构的巨量努力消耗在"把冯·诺依曼语言变得更胖"上**。所以我尽力分析常规语言的若干根本缺陷，并表明**除非我们发现一种新的语言框架，否则无法解决这些缺陷**。

寻找替代时——必须先认识到：**系统不能对历史敏感（让一段程序的执行影响后续程序行为）——除非系统有某种状态（前者可改它、后者可访问它）**——**因此历史敏感的计算系统模型必须有状态转换语义——至少在这一弱意义下**。**但这并不意味着每次计算都必须严重依赖一个复杂状态、且每一小段计算都伴随多次状态变化**（如冯·诺依曼语言）。

为说明替代——**我提议勾勒一类历史敏感系统**——其每一实例：

a) 具有**松耦合的状态转换语义**——一次重大计算中只发生一次状态转换；
b) **状态结构简单、转换规则简单**；
c) **重度依赖一个底层应用式系统**——既提供系统的基本程序设计语言、又描述其状态转换。

**我把这种系统称作"应用式状态转换系统（AST systems）"**——§14 描述。这些简洁系统避开了冯·诺依曼语言的许多复杂与孱弱，并提供一组强力且广博的可换部件。但本文勾勒它们只是**作为非冯·诺依曼系统这一广阔领域的粗略示例**——这一领域有多种迷人性质——我已研究三四年，**仍未为优秀语言必须解决的多重相互冲突需求找到令人满意的方案**——**但我相信这一探索已指明了设计非冯·诺依曼语言的一条有用进路**。

**这一进路涉及四要素**——其简纲如下：

a) **不带变量的函数式编程风格**：描述一个简单非形式 FP 系统——基于"用组合形式造程序"。给若干例子。
b) **函数式程序的代数**：变量在 FP 函数上取值、"运算"是 FP 函数式形式（FP 程序的组合形式）的代数——给出一些代数律——给出定理与例子，表明若干函数表达式如何被变换为等价的"无穷展开"，从而解释函数行为——并将 FP 代数与 Church 与 Curry 经典应用式系统的代数作比较。
c) **形式函数式编程系统（FFP）**：精确定义、提供使用 FP 风格及其程序代数能力的系统——可作 AST 系统的基础。
d) **应用式状态转换系统（AST）**：上述。

下文描述这四要素，给一些计算机设计上的简短评述，并以总结收尾。

## 11. 函数式编程系统（FP）

### 11.1 引言

我们对一类简单应用式编程系统（**FP**）作非形式描述——其"程序"就是不带变量的函数。下文继之以例子与对 FP 性质的讨论。

**FP 系统建立在一组固定的"组合形式（combining forms）"——称为函数式形式——之上**。这些（加上简单的定义）是从已有函数构造新函数的**唯一手段**——**它们不用变量、也不用代换规则**——并成为关联代数的"运算"。**FP 系统的所有函数都是单一类型**：把对象映为对象、永远只取一个参数。

而 λ 演算系统则建立在"λ 表达式 + 一组变量代换规则"之上——λ 表达式（连同代换规则）**能定义任意类型、任意参数数的所有可计算函数**。**这种自由与力量既有显然好处也有缺点**——它类似常规语言中"无限制控制语句"之力——**自由无度便是混沌**。**若像在 λ 演算中那样不断为场景发明新的组合形式——你对每个程序的代数律就**无人**真正理解**。本文 §11–§12 表明：**克制自己，仅用组合形式（而非 λ 表达式与代换规则）造程序——能换得对程序行为推理的能力，并把这种能力做进一组代数律**。

### 11.2–11.4 描述（要点）

**FP 系统四元组成**——**对象（objects）、函数（functions）、函数式形式（functional forms）、定义（definitions）**。

- **原子（atoms）** 与 **序列**：序列由其分量构成、长度可变；任一序列若含⊥则等于⊥（"序列构造保持⊥"）。例如 `<1, 2, 3>`、`<<A, 1>, B, <C, <2, 3>>>`。
- **函数**：把对象映为对象——所有函数都对未定义保留：`f:⊥ = ⊥`。原始函数包括 `selector` `1`, `2`, …、`length`、`+`、`-`、`×`、`÷`、`null`、`tl`（tail）、`tlr`、`distl`、`distr`、`apndl`、`apndr`、`reverse`、`rotl`、`rotr`、`trans`（transpose）、`pair`、`atom`、`eq`、`id`、`bu`（"binary to unary"）等。
- **函数式形式**：例如**复合** `f o g`，**构造** `[f₁, …, fₙ]`，**条件** `(p → f; g)`，**插入** `/f`，**全域应用** `α f`，**常量** `x̄`，**条件等等**。
- **定义**：`Def f ≡ <表达式>`。

#### 例子（FP 程序）

**矩阵乘法（MM）**——

```
Def MM ≡ (αα IP) o (α distl) o distr o [1, trans o 2]
```

意思（粗略）：以 `<m, n>` 为输入、`distl/distr` 把每个左行与右每列做配对成对子的矩阵——**对每个对子施 IP（内积）**——得到结果矩阵。**全过程不命名参数、不写循环、不带变量**。

### 11.5 FP 系统的性质讨论

- **不命名变量**——避免代换规则、把"组合"放回到主舞台。
- **静态结构**——可由结构推理；**易代数变换**。
- **有限"组合形式"**——必须就常见编程模式建立丰富的组合形式（如条件 `→`、构造 `[ … ]`、复合 `o`、α 应用等）。
- **限制是"不能定义任意可计算函数"**——但**这是为换取代数良好性而支付的代价**。

## 12. FP 程序代数

### 12.1 引言

**为 FP 系统建立"程序代数"**——**变量在 FP 函数上取值、"运算"是 FP 系统的函数式形式**。给出 24 条代数律——例：

| 律 | 形式 |
| --- | --- |
| 1 | `[f₁, …, fₙ] o g = [f₁ o g, …, fₙ o g]` |
| 2 | `α f o [g₁, …, gₙ] = [f o g₁, …, f o gₙ]` |
| 3 | `(f o g) o h = f o (g o h)` |
| 4 | `1 o [f₁, …, fₙ] = f₁`（依此类推） |
| … | … |
| 24 | `(p → f; g) o h = (p o h → f o h; g o h)` |

接着以**两条"展开定理"（expansion theorem）**给出一类方程的"解"——把方程的"未知函数"表示为一种**无穷条件展开**——**这一展开等于该函数的逐情形描述**——**并立刻给出终止的充要条件**。由此推出 **"递归定理"** 与 **"迭代定理"**——给出一些"线性方程"现成展开。例子：

- **阶乘**的递归与迭代版本——证明它们等价；
- **两个等价的迭代程序**之等价证明；
- "二次方程"——证其解为幂等函数。

把 FP 代数与 λ 演算等经典应用式系统的对应代数比较——**表明 FP 系统受限严格反而带来若干好处**——并就"算法地把函数归约到无穷展开"以及"在各种'懒求值'方案中应用"等问题作了若干提问。

## 14. 应用式状态转换系统（AST）

### 14.1 引言

把 FFP 系统作为底层应用式子系统——**外层加一个含状态的 AST 系统**——**每次重要计算只发生一次状态转换**。

### 14.2 AST 与 Algol 结构对比

| | Algol（冯·诺依曼） | AST |
| --- | --- | --- |
| 语义 | 与状态紧耦合——每条语句改变状态 | 与状态弱耦合——一次重要计算改变状态一次 |
| 表达式 vs 语句 | 二者分裂 | 同一应用式语言 |
| 命名 | 复杂命名约定与代换规则 | 名字即函数 |
| 可换部件 | 有限 | 几乎所有特性都可作可换部件 |

### 14.3 AST 系统的状态、输入与输出

- **状态 D**：序列形式——含一组"单元（cells）"——每单元 `<name, value>`；
- 一次输入 `<key, operand>` —— `key` 描述输入类（系统变更/表达式/程序/查询/更新等）；
- 转换：根据 key 选择函数应用、产生输出与新状态。

### 14.4 一个系统程序的例子

文献给出 `system`、`subsystem`、`update`、`query-response`、`report-update` 等 FP 定义，并展示如何通过两个输入把它装入一个最初空状态的 AST 系统——以及如何随后用它执行表达式（如 `(MM o [↑M, ↑N] o DEFS:#)` 计算两矩阵之积）。其要旨在于——**整个"系统的程序"亦由 FP 表达——可被代数变换与推理**。

### 14.5 AST 系统的变体

提议引入 **"系统形式（system forms）"**——以 AST 系统为参数构造新 AST 系统——一如函数式形式以函数为参数构造新函数——形成一种"系统代数"。

### 14.6 AST 系统简评

a) **每次重要计算一次状态转换**——可有有用数学性质——**消除了"语言上的"冯·诺依曼瓶颈**。
b) 程序以应用式语言写——**可换部件的力与灵活超过迄今任何冯·诺依曼语言**。
c) 在 `system : x` 计算期间状态不变——**所以无副作用**——**独立的应用可并行求值**。
d) **可在不改框架的前提下任意时刻引入主要新特性**——例如多种命名系统、类型/类型检查、通信并行进程、非确定性、Dijkstra 守卫命令、改进的结构化编程——**这些在冯·诺依曼语言里都必须建进框架**。
e) AST 框架 = 底层应用式系统的语法语义 + 上述粗框架——**按当下标准，这是极小的语言固定部分**。

### 14.7 AST 与冯·诺依曼模型中的命名系统

AST 中**命名由函数完成**——可用 `push`、`pop`、`purge`、带类型 `fetch` 等定义许多有用的"存取函数"——**这些定义与各自命名系统的引入不需更改 AST 框架**。**不同种类的"存"（如带"类型化单元"）可在同一程序里使用——一存中的某单元可包含另一整存**。**关键在于：AST 命名系统利用了名字的函数性**——名字函数可被复合、可被函数式形式与别的函数组合。**与之相反——冯·诺依曼语言中函数与名字常是不相交概念，且名字的"类函数性"几被掩盖、无可使用**：a) 名字不能作函数应用；b) 没有把名字与别的名字/函数组合的通用手段；c) 名字函数所作用之物（"存"）不可作为对象访问。

**冯·诺依曼语言不把名字当作函数处理——也许是它们更重要的弱点之一**。**任何情况下——把"名字作函数、存作对象"的能力都可能成为一个有用且重要的编程概念，值得彻底探索**。

## 15. 计算机设计简评

冯·诺依曼语言的优势让设计者**几乎没有什么"冯·诺依曼计算机的变体"以外的实用设计模型**。**数据流模型** [1, 7, 13] 是另一类历史敏感模型。**基于 λ 演算的语言的代换规则给机器设计者带来严肃问题**。Berkling [3] 发展了一种修改过的 λ 演算（含三种应用、不需变量重命名）并造了机器——**仍需更多经验来表明其作为有效编程风格之基础是否足够扎实，及其机器能多高效**。**Magó** [15] 用同样的部件（两类）造出一种新颖的应用式机器——**自底向上直接求值 FP 类与其他应用式表达式**——**没有冯·诺依曼存储、也没有地址寄存器，因此没瓶颈**——**能并行求值许多应用——其内置运算更像 FP 算子、不像冯·诺依曼计算机操作**。**这是我所见与冯·诺依曼计算机最远的偏离**。

种种迹象表明应用式风格能比冯·诺依曼风格更有力——**因此程序员应当发展一类新的、体现这种风格、并避开 λ 演算系统所附带的内禀效率问题的、对历史敏感的计算系统模型**。**只有当这些模型与其应用式语言已被证明胜过常规语言——我们才有经济基础去发展能最佳实现它们的新型计算机**——**也许只有那时——我们才能在不被冯·诺依曼瓶颈所限的设计中充分利用大规模集成电路**。

## 16. 摘要

**§1.** 常规程序设计语言大、复杂、不灵活——其有限的表达力不足以正名其规模与代价。

**§2.** 程序设计语言之下的计算系统模型粗分三类：(a) 简单操作模型（如图灵机）；(b) 应用式模型（如 λ 演算）；(c) 冯·诺依曼模型（如常规计算机与语言）。**每类都有重要困难**：(a) 程序晦涩；(b) 模型不能从一程序保留信息到下一程序；(c) 基础不可用、程序在概念上不有助。

**§3.** 冯·诺依曼计算机围绕一条瓶颈而建——**连接 CPU 与存储的"逐字管道"**——**程序必须借由通过此瓶颈泵大量字才能在存储中做整体改变**——**我们因此长出了"关心通过瓶颈的逐字流量、而非问题更大概念单元"的编程风格**。

**§4.** 常规语言基于冯·诺依曼计算机的编程风格——**变量 = 存储格；赋值 = 取/存/算；控制语句 = 跳转与测试指令；":=" 是语言的冯·诺依曼瓶颈**。**冯·诺依曼语言把编程切成"表达式世界（有序）与语句世界（无序）"——结构化编程稍稍简化语句世界，却没攻击根本问题——分裂本身与逐字风格**。

**§5.** 比较两种内积程序——**冯·诺依曼版本重复、逐字、只对长 n 的两定名向量奏效——靠过程声明才能通用——其语义复杂**。**函数式版本不重复、把向量当作整体处理、分层、完全通用——通过组合高层管家算子产生"管家"操作——不命名参数、无须过程声明**。

**§6.** 程序设计语言由"框架 + 可换部件"构成。**冯·诺依曼语言的框架要求大多数特性都被建进它**——只能容纳有限可换部件——因为"状态及其转换规则"必须为可换部件的所有需要做出详细规定（同时也要为框架内置的所有特性做出规定）。**冯·诺依曼框架不灵活的原因是其语义与状态紧耦合：计算的每一细节都改变状态**。

**§7.** **冯·诺依曼语言的可换部件表达力小**——**正因如此，多数语言必须建进框架**。**表达力之少源于冯·诺依曼语言不能有效使用组合形式来造程序——这又源于"表达式与语句的分裂"**。**组合形式在表达式中表现最佳——但冯·诺依曼语言的表达式只能产生一字结果，于是表达式世界中的表达力大半丧失**。**精巧的命名约定是另一阻碍**。

**§8.** **APL 是首个不基于 λ 演算、不逐字、并使用函数式组合形式的语言**——但它仍保留了冯·诺依曼语言的许多问题。

**§9.** **冯·诺依曼语言不具备推理程序所需的有用性质**。公理与 denotational 语义是描述/理解常规程序的精确工具——**但它们只**谈论**程序，不能改变其笨拙性质**。**与冯·诺依曼语言不同，普通代数的语言既适合表述自身规律，又适合在"语言内部"把方程变成解**。

**§10.** **历史敏感语言中——程序可影响后继程序**——**任何这种语言都需某种状态转换语义——但它不需要"与状态紧耦合、每一细节都改变状态"的语义**。**应用式状态转换（AST）系统**作为冯·诺依曼系统的历史敏感替代被提出——它具有：(a) **松耦合**的状态转换语义（一次重要计算一次转换）；(b) **简单的状态与转换规则**；(c) **简单"归约语义"的底层应用式系统**；(d) 一种"基于底层应用式系统及其语义"的程序设计语言与状态转换规则。**§11–§14 描述这一非冯·诺依曼语言/系统设计进路的诸要素**。

**§11.** 描述一类**不带变量的非形式 FP 系统**——每个系统由对象、函数、函数式形式、定义构成——**函数把对象映为对象**——**函数式形式由已有函数造新函数**——本节列例子讨论 FP 的局限与好处。

**§12.** 描述 **"程序代数"**——变量在 FP 函数上取值、"运算"是函数式形式——给约 24 条律——例子：证明非重复矩阵乘法程序与递归程序等价。下一小节给出两条**展开定理**——**"解"两类方程**：把"未知函数"表示为无穷条件展开（其逐情形地描述函数行为，并立刻给出终止充要条件）——并由此推出 **"递归定理"** 与 **"迭代定理"**——给出一些"线性"方程的现成展开。例子：(a) 递归与迭代阶乘函数的正确性证明；(b) 两个迭代程序等价之证；最后例子处理"二次"方程，证其解为幂等函数。再下一小节给出两条展开定理之证。

把 FP 代数与 λ 演算等经典应用式系统的代数比较——**表明 FP 这种"严格受限的"系统反带来若干好处**——并就"算法地把函数归约为无穷展开"以及"在多种'懒求值'方案中之使用"提出问题。

**§13.** **形式函数式编程系统（FFP）**——把 FP 系统的行为加以扩展并精确化——**其语义比经典系统简单——并能由简单不动点论证证一致性**。

**§14.** 比较 Algol 的结构与 AST 系统——描述使用一个 FFP 子系统的 AST 系统——给出其简单状态与转换规则——刻画一个**自我保护的小系统程序**及其安装/使用方式（文件维护、运行用户程序）——并简略讨论 AST 变体与可定义于 AST 内的"函数式命名系统"。

**§15.** 简略讨论应用式计算机设计的工作——以及发展并测试更实用的应用式系统模型作为该设计未来基础的需要。
