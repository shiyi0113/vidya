# 计算机系统设计的若干提示

**Butler W. Lampson · Xerox 帕罗奥多研究中心 · 1983年7月**
*原文 9th ACM Symposium on Operating Systems Principles，*Operating Systems Review* 15:5, Oct. 1983, pp. 33–48*

## 摘要

研究若干计算机系统的设计与实现，得出了一些**通用的系统设计提示**。本文把它们列出来，并以大量例子（从 Alto、Dorado 这类硬件，到 Bravo、Star 这类应用程序）说明。

## 1. 引言

**设计计算机系统与设计算法非常不同**：

- 外部接口（即需求）**定义得不那么精确，更复杂，更易变**；
- 系统拥有**远多得多的内部结构、因此有许多内部接口**；
- "成功"的衡量方式**远不那么清晰**。

设计者常发现自己在大量可能性的海洋里挣扎——**不清楚某个选择会如何限制后续选择，或如何影响整个系统的体量与性能**。**通常根本不存在"最佳"做法**——更重要的是：**避免糟糕的选择，并在各部件之间清晰划分责任**。

我设计并造过若干计算机系统——有的工作、有的不工作——也使用并研究过许多别人的系统。**由这些经验得出一些通用的设计提示**——我并不主张其中的任何一条新颖；多数是有经验设计者的"民间智慧"。然而即便专家也常常忘记——**而第二个系统 [6] 之后还有第四个**。

**免责声明**：这些提示**不是**——

- 新颖的（少数例外）；
- 万无一失的菜谱；
- 系统设计或操作的"定律"；
- 表述精确的；
- 自洽的；
- 总适用的；
- 被所有顶尖专家认可的；
- 或保证奏效的。

**它们就是提示**。有些相当一般而模糊；另一些是颇专门、应用面比许多人意识到要广的特定技术。所有提示与示例都不可避免地被简化了。**许多有争议**。

我尽量避开"模块化的劝勉、自顶向下/自底向上/迭代式设计的方法学、数据抽象的技术"这类已被广泛传播的内容——**有时我反而会指出这些时髦方法被鲁莽采用时的陷阱**。

> **这几条戒律装进你心里——/ 留意化为你的品格。**（莎士比亚《哈姆雷特》）
>
> 给一份关于"设计这件不靠谱事"的指南，配上《哈姆雷特》的引语，似乎再合适不过。除非另有标注，引语都来自波洛涅斯对莱阿提斯的劝告（I.iii.58–82）。每条引语都用以呼应紧接其后的文本。

每条提示由一句**口号**概括，**当被恰当解读时揭示该提示之精髓**。**图 1**沿两轴组织所有口号：

- **为何**有助于做好系统：功能性（它能做事吗？）、速度（够快吗？）、容错性（它能持续工作吗？）；
- **在系统设计的哪里**有所帮助：完备性、接口、实现。

| 何处 \ 为何 | 功能性（能工作吗？） | 速度（够快吗？） | 容错（能持续工作吗？） |
| --- | --- | --- | --- |
| **完备性** | 把"正常情形"与"最坏情形"分开 | 卸载（Shed load）；端到端；安全第一 | 端到端 |
| **接口** | 把一件事做好（Do one thing well）：不要泛化；做对它（Get it right）；不要把能力藏起来；用过程参数；留给客户；保持基础接口稳定；留一处可立足之地 | 让它快；分割资源；静态分析；动态翻译 | 端到端；记录更新（Log updates）；让动作原子化（atomic） |
| **实现** | 计划要丢掉一个；保留秘密（Keep secrets）；好主意再用一次；分而治之 | 缓存答案；用提示（hints）；用蛮力；后台计算；批处理 | 让动作原子化；用提示 |

## 2. 功能性

最重要、也最模糊的提示与"获得正确功能"有关——也就是让系统去做你想做的事。多数提示依赖于"接口"这一概念——**接口把抽象的实现与使用该抽象的客户分开**。

> **两个程序之间的接口由"每个程序员为证明自己程序正确性所必须对另一程序作出的假设的集合"构成**（[5] 的释义）。

**定义接口是系统设计中最重要的部分**。也常常是最难的——**接口设计必须满足三项相互冲突的要求：简单、完备、能容下一个充分小且快的实现**。可叹的是，体现于接口里的假设**常常被证明是误识**。Parnas 的经典论文 [38] 与一篇较新的关于设备接口的文章 [5] 在此话题上提供了卓越的实操建议。

**接口难设计的主要原因是**：每个接口都是一种**小型编程语言**——它定义了一组对象与一组可对这些对象施加的运算。**具体语法不是问题——但程序设计语言设计的几乎每一个其他方面都在其中**。Hoare 在语言设计上的提示 [19] 因此可视为本文的补编。

### 2.1 保持简单

> **完美——不是无可添加之时——而是无可删除之时。**（圣埃克苏佩里）
>
> **既得朋友、且经验证——以钢箍把他们扣紧到你的灵魂里——但勿以接待每位新孵化的伙伴而磨钝你掌的锐利。**

**Do one thing at a time, and do it well（一次只做一件事，并把它做好）**。**接口应抓住一个抽象的最少本质**。**不要泛化——泛化往往出错**。

> **我们正面临一个无可逾越的良机。**（W. Kelley）

接口若承担过多——其实现大概会大、慢、复杂。**接口是一份"提供一定服务"的合同**——客户依赖这份合同——通常合同被写在接口规约里。**他们也依赖于"使用接口的代价合理"**——而"合理"通常没有写在任何地方。**若有 6 层抽象，每一层比"合理"贵 50%，最顶层交付的服务就会差出 10 倍以上**。

> **KISS：Keep It Simple, Stupid。**——（佚名）
> **若有疑虑，把它去掉。**——（佚名）
> **消灭特性。**——（C. Thacker）
>
> 反过来：**一切都应当尽可能简单——但不应再简单。**——（爱因斯坦）

**所以服务必须有相当可预测的代价**——**接口不应许诺超过实现者所知如何交付的东西**——尤其不应许诺只对少数客户有用、又不知如何在不惩罚他人的前提下提供的特性。也许后来更好的实现者能做到——但**除非你这一位能做到，明智之举是降低期望**。

**例如 PL/I 因为试图为大量"通用运算"在大量数据类型上提供一致含义而陷入严重麻烦**。早期实现处理所有情形都低效——**即使十五年后有了优化编译器，程序员仍很难判断什么会快、什么会慢** [31]。Pascal、C 这种语言更易用——**因为每个构造的代价大致与上下文或参数无关——并且大多数构造的代价相近**。

当然这些观察主要适用于客户**频繁使用的接口**——虚存、文件、显示、算术。在不常用的接口（密码校验、解释用户命令、72 点字符打印）里**为功能牺牲一点性能是可以的**——**意思是：代价虽仍要可预测，但可以是最小可达代价的若干倍**。**这条审慎的规则不适用于"目标为'弄清如何做更好实现'的研究**——但研究可能失败，**别人不能依赖其成功**。

> **Algol 60 不仅是其前辈的进步——也几乎是其全部后继者的进步。**——（C. Hoare）

**"提供过多"的例子比比皆是**。Alto 操作系统 [29] 有"普通的 read/write-n-bytes"文件接口——为 Interlisp-D [7] 扩展的分页系统把每个虚存页存到一个专用磁盘页上——两者的实现都很小（文件 ~900 行代码、分页 ~500 行）且很快（一次缺页一次磁盘访问，CPU 计算开销只占磁盘访问时间的一小段；几扇区缓冲就能以盘速扫整盘）。Pilot 系统 [42]（Alto OS 的继任者）效仿 Multics 等系统——允许虚存页映射到文件页，**把文件 I/O 纳入虚存系统**。**实现大得多（约 11,000 行）、慢得多（一次缺页常带来两次磁盘访问，且无法以盘速运行）**——**这"额外功能"代价不菲**。

> **而这一结局——将设计者的本意变作落到自己头上的祸患**。（V.ii.387）

另一例展示泛化如何容易导致意外复杂：**Tenex** [2] 有这套"看起来人畜无害"的特性组合：

- 引用未分配虚存页时，通过陷阱报告给用户程序；
- 系统调用被视作"扩展机器的一条机器指令"——它对未分配虚存页的引用同样被报告给用户程序；
- 系统调用的大参数（包括字符串）按引用传递；
- 有一个 `CONNECT` 系统调用以获得另一目录的访问权；其参数之一是含目录密码的字符串——若密码错，则 3 秒后才返回失败，以阻止高速猜密码。

`CONNECT` 实现大致为：

```
for i := 0 to Length(directoryPassword) do
    if directoryPassword[i] ≠ passwordArgument[i] then
        Wait three seconds; return BadPassword
    end if
end loop
connect to directory; return Success
```

如下小把戏可平均用 64n 次而不是 128n/2 次（Tenex 字符串用 7 位字符）找到长度为 n 的密码——**把 `passwordArgument` 摆成"它的第一个字符位于某页的最后一字节、下一页未分配"**——逐个尝试每个可能的首字符——**若 `CONNECT` 报 BadPassword，猜错；若系统报"对未分配页的引用"，猜对**——再依次推进第二字符……

**这个隐晦但有趣的 bug 没被设计者发现——因为 Tenex 系统调用所提供的接口相当复杂**：它包含了"对未分配页的引用被报告"这一可能性。或换个角度看——**系统代码中一条普通取址指令的接口也相当复杂**——它包含了"非法引用会被报告给客户、而系统代码无机会先行获得控制"这一可能性。

> **工程师就是能用一毛钱做任何傻瓜要花一块钱才能做之事的人**。

**有时值得花大力气把一个干净有力的接口实现得很快**。若接口被用得足够广，**所投入的设计与调优能加倍偿还**。但只对那种**重要性已被既有用法所证实**的接口这样做——**而且要确信你知道如何把它做快**。

例如 BitBlt（RasterOp）接口 [21, 37]——Dan Ingalls 在使用 Alto 高分辨率交互显示器多年后构思出来——**其实现耗费的微码与 Alto 标准指令集模拟器整体相当，需要大量技艺与经验**——但其性能几乎与之前的"专用字符栅格化"操作相当，**简洁与通用让做显示应用容易得多**。Dorado 内存系统 [8] 含一个 cache 与一条独立的高带宽 I/O 通道——**每 64 ns 周期一次 cache 读写、500 Mb/s I/O 带宽、cache 与 I/O 都做虚拟寻址**——实现 850 个 MSI 芯片、几年人时——**这只能由对该接口的长期经验（30 年！）和"内存访问通常是性能瓶颈"的认识来正名**。即便如此，事后看**高 I/O 带宽并不值——它主要给显示用，双口 framebuffer 几乎肯定更好**。

最后，免得这条建议看着太轻——

**Get it right（把它做对）**——**抽象与简洁都不能替代"做对"**。事实上抽象本身可以是严重困难的来源——下面这则故事便是一例：办公文档系统通常允许在文档中嵌入命名字段——例如表单信里的 `address`、`salutation`。文档常用字符序列表示，字段编码为 `{name: contents}`。在诸多操作之中有一个 `FindNamedField` 找指定名字的字段。某主流商业系统所用 `FindNamedField` 一段时间内是 O(n²) 的——**这是怎么实现的**？先写了 `FindIthField` 找第 i 个字段（无辅助结构，必然 O(n)）——再以非常自然的方式实现 `FindNamedField(name)`：

```
for i := 0 to numberOfFields do
    FindIthField; if its name is name then exit
end loop
```

一旦选了这个不明智的 `FindIthField` 抽象——**只有对其代价有敏锐意识，才能避免这种灾难**。**这不是反对抽象——但要时刻警觉抽象之危险**。

### 2.2 推论

"简单与不要泛化"这条规则有许多有趣推论。

> **行头要尽你财力之奢——但勿涉于花哨；要厚重，不要俗艳**。

- **让它快，而不是通用或强力（Make it fast, rather than general or powerful）**。**只要它快，客户能编出他想要的功能**——另一个客户可能需要别的功能——**让基本运算执行得快，远胜让"更强力的运算"慢吞吞地完成**（当然，又快又强是最好的——前提是你知道怎么做到）。**慢而强力的运算的麻烦在于：不需要那些"强力"的客户也为基本功能多付了钱**——而且**"强力运算"经常不是对的那种**。

> **若我有时间——但这位严酷的死神已不容我延宕——哦，我本可告诉你——但就此打住**。（V.ii.339）

许多研究（[23, 51, 52]）表明——程序绝大多数时间都在做非常简单的事：load、store、相等比较、加 1。**像 801 [41] 或 RISC [39] 这种"把简单运算做快"的机器——以同等硬件能跑得比 VAX 那种"指令更通用更强力但简单情形耗时更长"的机器更快**。**程序运行时间在硬件量相同时翻一倍很容易**——更"宏伟"的"客户需要什么"的设计反而更糟 [18]。**要找出大型系统里时间花在哪——必须有测量工具**。**80% 的时间花在 20% 的代码里很常见——但靠先验分析或直觉通常找不准这 20%**。Interlisp-D 借助一组有效工具，性能调优后总速提升了 10 倍 [7]。

- **不要把能力藏起来（Don't hide power）**。当一个低层抽象允许某事被快速做到——**更高层不应把这种能力埋在更"通用"的东西里**。**抽象的目的是隐藏不可取的性质；可取的性质不应被隐藏**。当然抽象有时需要多路复用资源——这必有一定代价——**但应当能把全部或几乎全部资源以仅微小性能损失交付给单一客户**。
   例：Alto 磁盘硬件 [53] 能以盘速传一整柱面。基本文件系统 [29] 能以盘速把连续文件页传到客户内存——客户每扇区有时间做一些计算——**只需几扇区缓冲，整盘可被以盘速扫描**。这个能力已被用于多种应用：从重建破损文件系统的"清扫器"到模式匹配文件搜索。文件系统的 stream 层可读写 n 字节——**若 n 字节中任何"完整盘扇区"段，都以盘速传输**。**加载器、编译器、编辑器与许多程序的性能都依赖于此读大文件的能力**。在该层，客户放弃了"看到页到达"的能力——**这是更高抽象层付的唯一代价**。

- **用过程参数为接口提供灵活性（Use procedure arguments）**。需要时可在保护或可移植性上对它做限制或编码——**这一技巧能极大简化接口、消除那些等同于一种小语言的杂乱参数**。简单例子是返回"集合中所有满足某性质元素"的枚举过程——**最干净的接口是让客户传一个测试该性质的过滤过程，而不是定义某种模式语言**。这种主题有许多变奏：Berkeley 940 系统的 Spy [10] 让"不可信用户程序"可以在主管代码中植入补丁——补丁以机器语言写成，但安装时验证它没野跳转、不含循环、不太长、只写到专门统计区域——**学生由此能在不破坏系统的前提下做精细测量**。Cal 6400 的 `FRETURN` 机制 [30] 给出从任意主管调用 C 派生 CF 的能力——**正常情形下与 C 速度一致；C 出错则把控制送往指定的失败处理**——CF 还可做更多（如把"快但小容量存储"的文件扩展到"慢但大容量存储"）——但**正常情形下与 C 同样快**。
   不过当**专门语言更便于做静态分析以优化**时，专门语言可能更好——这是数据库查询语言设计的一个主要判据。

- **留给客户（Leave it to the client）**。**只要跨接口传递控制的开销低，接口就能"只解决一个问题、把其余留给客户"——同时具备简洁、灵活与高性能**。例如许多解析器只做"上下文无关识别"，并调用客户提供的"语义例程"记录解析结果——**这显然优于总是构造一棵让客户去遍历的语法树**。Monitor [20, 25] 作为同步装置之所以成功，部分是因为锁与信号机制做得很少——**真正的工作交给 monitor 过程内的客户程序**——这让 monitor 实现简洁且快——若客户需要缓冲分配、资源记账或别的功能，自己实现或调用别的库设施——**为所需付费**。Monitor 不给在锁或条件变量上等待的进程的调度提供控制——常被指为缺点——**实际上是优点**——它把调度自由留给客户（用一组条件变量而非"内置但常做不对"的机制）。Unix [44] 鼓励构建小程序——**取若干字符流为输入、产出若干流、做一件事**——当此风格被恰当效法时，**每个程序都有简单接口、做一件事做得好——客户把多个组合起来，配合自己的代码精确达成所欲效果**。
   §3 谈到的"端到端"口号也是"保持简单"的另一推论。

### 2.3 连续性

设计**改进**的渴望与**稳定/连续**的需要之间存在持续张力。

- **保持基础接口稳定（Keep basic interfaces stable）**。接口体现了被多于一处共享的假设——**有时是被大量地方共享**——**很想不要改它**。在没有类型检查的语言里，**改公共接口几乎不可能**——因为没法追到所有客户、做基本兼容性检查。带完备类型检查与语言级接口支持的语言（如 Mesa [15]）则容易得多——**但即便类型检查能发现"假设不再成立"，程序员还是必须去修正它**。一个系统涨到 25 万行以上时，**变更的总量便变得不可承受**——即便毫无疑问要做什么，**做这件事所需时间都过长**——**只能把系统切成更小的、由"几年都稳定的接口"相联的部分**。传统上，**只有编程语言或操作系统内核所定义的接口能稳到这个程度**。

- **如果非改接口不可，留一处可立足之地（Keep a place to stand）**。两个迥异的例子：**兼容包**——在新系统之上实现旧接口——让依赖旧接口的程序继续工作。新 OS（如 Tenex [2]、Cal [50]）通过模拟旧系统的主管调用（TOPS-10、Scope）使旧软件可用——**通常仅需对比"重做旧软件"小得多的努力**。IBM 360/370 系列对 1401、7090 等旧机器指令集做仿真——再走一步就是**虚拟机**——在机器自身上仿真该机器的（多份）副本 [9]。
   另一种例子是"**世界交换调试器（world-swap debugger）**"——把目标系统真实内存写到二级存储——把调试系统装进去——再把目标内存换回继续执行——**这有点笨重，但允许在系统极低层很方便地调试——因为调试器除了那个"非常简单的世界交换机制"之外不依赖目标里任何其他东西的正确**——**bootstrap 时尤其有用**。变奏很多——例如调试器可在另一台机上跑，目标里只放一段小"远程调试 nub"，能解释 ReadWord/WriteWord/Stop/Go——或目标是分时系统中一进程时，调试器可在另一进程里跑。

### 2.4 让实现工作

> **完美须循序而至——她需要时间的徐徐之手**。（伏尔泰）

- **计划要丢掉一个；反正你也要丢（Plan to throw one away; you will anyhow [6]）**。如果系统有任何新功能，**第一份实现一定要被完全重做，才能达到令人满意（足够小、足够快、可维护）的结果**——**计划做一个原型，能省很多**。可惜——**有时需要两个原型**——尤其创新很多时。如果幸运，可以从前作大量复用——Tenex 基于 SDS 940 [2]——**即便前作过于宏伟也行**——Unix 从 Multics 借了许多想法 [44]。**即便实现成功，系统演化时也值得回头审视旧决定**——尤其那些为载荷或环境（如内存大小）的特定属性而做的优化常常已不再适用。

> **思想勿出口——不成比例的念头勿付诸行动。**

- **保留实现的秘密（Keep secrets of the implementation）**。"秘密"是**客户程序不被允许做的关于实现的假设**（[5] 的释义）。也就是说——**它们是可以变的；接口定义的是不能变的**（除非同时改实现与客户）。显然，**当各部分对彼此假设更少时——系统更易编程与修改**。另一面，**系统不一定更易设计**——**好接口难设计**——并且**与"不要藏起能力"存在张力**。

> **高效的程序是逻辑边缘试探之练习**。（Dijkstra）

**保留秘密还有一种危险**：提升性能的一种方法是**让一部分对另一部分作出更多假设**——这些额外假设常常允许**少做事——有时能少很多**。例如若大小为 n 的集合已知有序——成员测试就只需 log n 而不是 n。**算法设计与小模块调优中这种技术非常重要**。但在大型系统中，**能独立改进每一部分通常更重要**——**找到平衡仍是艺术**。

> **哦，把那更糟的一半丢掉——以另一半更纯净地活下去**。（III.iv.157）

- **分而治之（Divide and conquer）**。把难题归约为若干更易题——结果通常是递归的。**资源受限时该方法略变形**：**咬下能咬下的那么多，剩下的留给下一次迭代**。
   Alto 的 Scavenger 程序扫盘并由每扇区记录的文件标识与页号重建文件系统的索引与目录结构 [29]。其重写版有一阶段：**在主存中建一个数据结构——文件中"既连续在盘上、又连续在文件中的页段"的每段一个条目**。通常文件分配大致连续——结构不大；若盘碎得厉害，**结构装不下主存**——这时 Scavenger **丢一半文件的信息、用另一半继续**——重建完后再为另一半重复——必要时进一步细分——**只有"单文件索引装不下"时方法才会失败**。
   另一例是 Dover 栅格打印机 [26, 53] 把字符与矩形扫描转换为巨大 m × n 比特阵列——其中 m=3300、n=4200——**14M 比特装不下内存**——而**打印机消耗位的速度比可用磁盘提供的快**——所以阵列也无法全放盘上。整阵列被切成 16 × 4200 的"带（band）"——电子部分含两个一带的缓冲——字符与矩形按"起始所在带"分桶——扫描转换：从一个桶填满一带缓冲，把它送给打印机的同时清零并从下一个桶填另一缓冲——**跨带的对象被加到下一个桶**——这便是"问题可被细分"之诀。
   有时把资源人工地按固定大小**量化**很方便——简化记账、阻止某种碎片化。**经典例子是虚存用固定大小页而非可变大小段**——尽管"把逻辑相关信息放一起、整体在主/次存间传输"看起来更优——**分页系统终究表现更好**——其原因复杂、未被系统研究。

> **而宁愿忍受我们已有的痛苦，也不飞向我们不识的痛苦**。（III.i.81）

- **重用一个好主意而不是泛化它（Use a good idea again instead of generalizing it）**。"专门化的实现"常常远比"通用化"更有效。下面缓存一节给出多个例子。另一例：**为可靠性复制数据**——少量数据可以容易地本地复制（写到两个或更多盘上 [28]）；当数据量大或必须放在不同机器上，**保证拷贝总相同就难了**——Gifford [16] 在事务存储之上构建复制数据，使任意大更新可作为一原子操作完成（参见 §4）；**事务存储本身则依赖那种简单的本地复制方案存其日志**——**这里不是循环——只是这个"主意"被用了两次，代码并没**。第三种把复制用到此处的方式是**把提交记录存到多台机器** [27]。
   Star 办公系统 [47] 的 UI 有一组小操作（敲字、移动、复制、删除、显示属性）——**几乎适用于系统中所有对象**：文本、图形、文件夹、抽屉、记录文件、打印机、收发件篮等。具体含义按对象类变化、在用户感觉自然的范围内（把文档复制到"发件篮"——它会被作为消息发出；移动一条线的端点——线像橡皮筋一样跟随）。**许多情况下实现差异很大**——但通用操作不只让系统更易用——**它代表一种"什么操作可能、各类对象如何组织实现"的视角**。

### 2.5 处理所有情形

> **绝望的疾病——靠绝望的处方得救——或根本无救**。（III.vii.9）

- **把"正常"与"最坏"分开处理（Handle normal and worst cases separately）**——两者要求迥然——
   - **正常情形必须快**；
   - **最坏情形必须有所推进**。

多数系统中，**调度不公允、对部分进程不提供服务、甚至让整个系统死锁——只要这种事件能被自动检测、且不太常发生——都可以接受**。常见恢复是**让某些进程崩溃、甚至整系统重启**。乍听很糟——但**每周一次崩溃通常是换取 20% 性能的便宜代价**。当然系统必须有像样的错误恢复（端到端原则的应用，参见 §4）——但这本就必需，因为崩溃成因甚多。

缓存与提示（§3）是"正常情形特殊处理"的例子，但还有许多。Interlisp-D 与 Cedar 编程系统使用**引用计数 GC** [11]，并有一个重要优化：**过程的局部帧（激活记录）中的指针不计数；GC 时扫描这些帧**——**这省去了大量计数**——大多数指针赋值是赋给局部变量；帧不多，扫描时间小，**收集器近乎实时**。Cedar 走得更远：不跟踪局部变量哪些含指针——**假定它们都是**——**这意味着碰巧含已不再被引用对象地址的整型数会防止该对象被释放**——测量显示 < 1% 的存储被错误保留 [45]。引用计数易做"增量收集"——但**收不回不再可达的环结构**——所以 Cedar 也有一个常规的 trace-and-sweep 收集器：**不适合实时**（要停整系统几秒）——但交互应用里可在喝咖啡时回收累积的环。引用计数另一问题是**计数可能溢出其位数**——发生很罕见（极少对象引用 > 2、3）——可让最大值"sticky"。可惜某些应用大结构的根被很多地方引用——一旦根 sticky——**意外地把大量存储变成永久**。一个吸引人的解：**"溢出计数"哈希表**——计数到上限时减半、在该对象上设溢出标志，溢出表 +1；计数到 0 时若有溢出标志反过来。**4 位足以计 7、溢出表在"计数摆动 > 4"时才被触动**。

资源动态分配/释放的多种情形（如分页系统的真实内存）——**有时释放一项还需暂存额外资源**（要换入某表才能知道把页写到哪儿）——通常有缓冲（"干净页"可零功夫释放）——**最坏时缓冲耗尽**（全是脏页）——窍门是**留点东西在床垫底下，只在危机才取**——必须**对"释放一项所需资源"作上限**——这便决定了"床垫下的预留量"——可被视为多路复用的固定开销。**危机来时一次只释放一项**——把全部预留专于此项——这或许极慢——**但能保证有所推进**。

有时正常与最坏需迥异策略。Bravo 编辑器 [24] 用**"块表（piece table）"**表示文档——一个"块"数组——指向存储在文件中字符串的指针——每块含起始字符的文件地址与长度——**串在编辑中从不被改**——例如删字符时——含该字符的块被切成两块；插入字符则把含插入点的块切三块；插入字符被追加到文件——长时间编辑后会有几百块——**性能拖慢**——这时**清理（cleanup）**：把文档全部字符按序写到新文件——块表替为单一指向新文件的块——**清理是一种特化 GC——可后台做**（Bravo 没这么做）。

## 3. 速度

> **既不要做借者，也不要做贷者——/ 借出常使二者皆失（朋友与本金）——/ 借入则磨钝了治家的锐利**。

- **若有疑虑，按固定方式分割资源（Split resources），而不是共享**。**专属资源通常分配更快、访问更快、分配器行为更可预测**。明显缺点：忽略多路复用开销时，**总资源量更多**。**多数情况下额外资源便宜，或开销大于碎片，或两者都成立**。
   例：访问 CPU 寄存器永远比从内存（即便高性能 cache）更快——**寄存器名声不好**因为聪明分配复杂、过程调用上的保存/恢复或抹掉其速度优势——**但当今"许多小过程"风格里，16 个寄存器几乎够所有局部变量与临时值——分配不成问题**。**用 n 套寄存器栈式排列**——只在 n 次连续调用未返回时才需保存 [14, 39]。I/O 通道、浮点协处理器等专用计算装置也是该原则的应用——**额外硬件昂贵时多路复用单一处理器；便宜时静态分配各种专用算力即可**。
   前述 Interlisp 虚存系统 [7] 需追踪每虚地址对应的盘地址——**这些信息可放在虚存中（Pilot [42] 这样做）——但要避免循环很复杂——所以专用真实内存放它**——除非盘碎得离谱——这块比"防循环代码"更小。

- **能用静态分析就用（Use static analysis if you can）**——这是上一条的推广。**静态分析发现的程序性质常可用来提升性能**——关键在"如果你能"——若做不出好的静态分析——**别拿糟糕的凑合，退回动态方案**。
   关于寄存器的论述依赖于编译器**容易决定如何分配**——把局部变量与临时值放进去就行。多数机器没有多套寄存器、或缺把它们高效栈化的方式——好分配就难了——需精巧的过程间分析（未必成功），并在程序每次变更时重做。**所以"小小动态分析（栈化寄存器）走很远"**——当然若编译器够聪明，大过程里静态分析仍很值。
   程序顺序读数据快得多——**容易预测并预读**——数据常可在盘上顺序分配——**至少一个数量级的传输加速**。这些性能提升依赖于程序员把数据安排得"按可预测模式访问"——也就是**静态分析可行**。**有许多事后分析程序、优化盘传输的尝试——据我所知都没奏效——按需分页所做的动态分析至少不输**。某些静态分析利用某种不变量被维护这一事实——若硬件失败或软件 bug 让不变量失效——这种系统就更脆。

- **动态翻译（Dynamic translation）**：**从"便利"（紧凑、易改、易显示）的表示动态翻译为"可被快速解释的"表示**——是"编译"这古老想法的重要变奏。**逐位翻译**便是**分别编译**之思想（追溯到 Fortran 2）；**增量编译器**在语句/过程被改时自动做。Mitchell 研究了"便利与快速表示之间连续运动" [34]。一种更简方式是**总按需翻译并缓存结果**——只需一个解释器，除缓存替换外不需其他决定。
   例：实验性的 Smalltalk 实现 [12] 用标准 Smalltalk 编译器产出的字节码作"便利表示"——过程被调用时把它从字节码翻译为机器码——保留几千条指令的缓存——**要奏效，缓存须足够大，使一过程平均被执行至少 n 次**——n 是翻译时间与未翻译代码执行时间之比。
   C-machine 栈缓存 [14] 是不同例子：指令进入指令缓存——加载时，相对于局部帧指针 FP 的操作数地址被转换为绝对地址（用过程执行期间常量 FP）——若结果地址在栈数据缓存当前范围内，则**操作数被改成寄存器模式**——稍后执行时直接在数据缓存里访问该寄存器——FP 与指令地址拼接做缓存键——使同一过程的多次激活能各自工作。

> **若你曾把我放在心里**。（V.ii.349）

- **缓存"代价昂贵的计算"的答案（Cache answers）**——把三元组 [f, x, f(x)] 存入以 f 与 x 为键的关联存储——**在 f(x) 未被替换前再次需要时查找取回**——加速幅度取决于 f(x) 有多昂贵。**严重问题**：当 f 不是函数（同参数可有不同结果）时，需要在 f(x) 变化时**使缓存条目失效或更新**——**更新依赖于形如 f(x + Δ) = g(x, Δ, f(x)) 的等式**，其中 g 远比 f 便宜算。例如 x 是 1000 个数的数组、f 是和、Δ 是改某个值（[i, v]）——则 g(x, [i, v], sum) = sum − xᵢ + v。
   太小的缓存（装不下所有"活值"）会**抖动**——若 f 重新计算很贵，性能会很糟——**所以缓存大小宜自适应**：命中率下降则增大、长时间未用则缩小。
   经典例子是加速主存访问的硬件——三元组 [Fetch, address, contents]——**Fetch 不是函数**：Store(x) 后 Fetch(x) 会变——**所以 store 之后必须更新或失效缓存**。**虚存系统也是这样**：主存扮演缓存、盘扮演主存——单位是页/段。
   几乎所有非平凡系统都有更专门的缓存应用——尤其在交互/实时系统——**核心问题是"对频繁小变化增量更新一个复杂状态"**——**ad hoc 做极易出错**——**最佳组织原则是"每次变化重算整个状态、但缓存所有该计算昂贵的中间结果"**——一次变化必须使**至少**那些被它弄无效的缓存条目失效；若太难精确识别，可让更多条目失效，代价是更多重算——**成功之诀是把缓存组织得让"小改动只让少量条目失效"**。
   例：Bravo 中 `DisplayLine(document, firstChar)` 返回当前显示文档中以 `document[firstChar]` 开头那一行的位图——同时返回 `lastChar` 与 `lastCharUsed`（行最后字符号、计算位图时检查的最后字符号——通常不同，因为为选断行需看过行尾）——它做断行、对齐、字符 → 栅格图。缓存为屏上每一行（有时上下几行）保留条目。改 i..j 字符的编辑使任何 [firstChar..lastCharUsed] 与 [i..j] 相交的缓存条目失效。**显示重算**：

```
loop
    (bitMap, lastChar, ) := DisplayLine(document, firstChar); Paint(bitMap);
    firstChar := lastChar + 1
end loop
```

若 `[document, firstChar]` 缓存条目存在则跳过 `DisplayLine` 调用。最后未被使用的条目被丢弃——它们并非无效，**只是不再有趣**——断行变了、再没行从那点开始。

同样思想用于很不同的设置——Bravo 允许文档分段（每段含左右页边、行间距等）——**普通分页所需信息很紧凑**：行数、每行高（一般同高）、保持属性（keep）、前后行距——通常三、四字节。30 页章节约 300 段——所有这些数据约 1k 字节——**比一页的字符规约还少信息**——**版面计算可与一页的行版面计算相当**——**所以为该章分页应少于"渲染一页"所需时间**——每章独立做即可。**让这一切奏效的是 [paragraph, ParagraphShape(paragraph)] 的缓存**——段被编辑时该缓存条目失效——可在编辑时（屏上时合理）、后台、或仅在请求重排页时重算。

> **衣装常昭显其人**。

- **用 hint 加速正常执行（Use hints to speed up normal execution）**。hint 像缓存条目，是某计算的保存结果——但有两点不同：**它可能错；不一定靠关联查找到达**。因为可能错——**采取任何不可逆动作前必须有验真之法**——**对照"truth"（必正确，但可为本目的而非高效执行做优化的信息）核验**。和缓存一样，hint 的目的是让系统更快——**通常需几乎一直正确**。
   例：Alto [29] 与 Pilot [42] OS 中每个文件有唯一标识，每个磁盘页有可读写时不影响传输的"label"字段——含该页所属文件标识与该页号；零号页是"leader"，含该文件所在目录与该目录中的字符串名——**这是文件系统赖以为生的 truth**——它们竭力维护其正确。**仅有这些信息无法快速做"按名找文件标识"或"找页 i 的盘地址"——只能扫整盘，能做但太慢**。所以两系统都维护 hint：**目录用一个含 [字符串名, 文件标识, 首页地址] 三元组的文件表示**；每个文件有一种结构把页号映到盘地址——**Alto 在每 label 加上"指向下一 label 的链"——使从页 n 到页 n+1 很快**；Pilot 用 B-tree 直接实现该映射，利用"连续文件页占用连续盘页"的常见情形。**所有这些 hint 用时都被核验**——校 label 或读 leader 的文件名——**若证错，全可由扫盘重建**。同样地——记空闲盘页的位表是 hint——**truth 是空闲页 label 中的特殊值**——分配时验、写文件标识与页号前覆写。
   另一例是 Arpanet [32] 最初的存转发路由——每节点保存"到每其他节点最佳路由"的表——**通过周期性广播更新——每节点告诉所有其他节点其对邻接链路质量的看法**——这些广播不同步、不保证抵达——**节点视图任意时刻可能不一致**——**truth 是每节点知自己身份**——剩下的，路由"尽力而为"——变化不太快时近最优。
   更有趣的例子是 Ethernet [33]——**线缆上无载波被作为"可发包"的 hint**——若两发送者同时取此 hint——发生**碰撞**（双方可探测）——双方停下、随机延迟、重试。**若连续 n 次碰撞——则取作"发送方数为 2ⁿ" 的 hint**——每个发送者把随机延迟均值设为初值的 2ⁿ 倍——**这"指数回退"防止网过载**。
   非常不同的应用——加速 Smalltalk [12]：Smalltalk 调用执行的代码由首参数类型动态决定——`Print(x, format)` 调用 x 类型里的 Print。**Smalltalk 没声明，类型编译期不知**——每个对象有指向 [proc 名, 代码地址] 表的指针——调用时查找——**贵**。**幸而 x 通常和上次类型相同**——所以 `Print(x, format)` 编为：

```
push format; push x;
push lastType; call lastProc
```

每个 Print 过程开头：

```
lastT := Pop(); x := Pop(); t := type of x;
if t ≠ lastT then LookupAndCall(x, "Print")
else <过程体>
```

`lastType`/`lastProc` 是代码内的立即值——`LookupAndCall` 应将 x 类型与所找代码地址回写到 `lastType`/`lastProc`——**下一次类型相同就直接调用**——**测量约 96% 命中**——指令取指能让 hint 正确时调用与普通子例程调用同快——`t ≠ lastT` 检查可不分支地实现。同样想法在 S-1 [48] 中以另一形式出现——**指令缓存为每条指令多一位**——加载时清、若指令使分支被取则置——指令取指依此选取走向；预测错则改位、走另一路。

- **若有疑虑，用蛮力（When in doubt, use brute force）**。**尤其随硬件价格下降，"直白、易分析、需大量专用算力"的方案往往胜过"复杂、特性不明、依赖特定假设才好用"的方案**。Ken Thompson 的 Belle 国际象棋机主要靠**专用硬件**生成走法、评估局面，而非精巧棋策——多次夺得世界计算机象棋冠军。另一例是**个人计算机胜过分时系统**——后者更"聪明"、浪费的周期更少——但前者越来越被认为是交互计算最具成本效益的方式。**渐近上更快的算法不一定更优**——比如有快于 O(n²·⁵) 的矩阵乘法——但常数因子高得令人望而却步。更平凡的例子：7040 Watfor 编译器对符号查表用线性搜索——**学生程序符号少，更好算法的启动开销收不回来**。

- **能后台就后台（Compute in background when possible）**。在交互/实时系统——**响应请求前少做事是好事**——快速响应对用户更好；负载常波动——**稍后通常有空闲的处理器时间做后台**。许多任务可推后台——Interlisp、Cedar 的 GC [7, 11] 几乎都后台做——许多分页系统在后台写脏页、备替换候选；电邮可由后台递送/取信（一两小时内即可）；许多银行夜间合并账户数据，次晨即用——**这四例对前后台同步的需求逐渐提高**——同步越多越要小心避免微妙错误（极端例参见 [13] 的"飞行 GC"）——**多数情形下两个独立进程间的简单生产-消费即可**。

- **能批就批（Use batch processing if possible）**——增量做几乎总更贵——盘磁带按序访问效果好得多；**批处理还允许更简单的错误恢复**。Bank of America 的交互系统让出纳记录存取——晨载入当日账户余额、白天竭力维持——**次日清晨在线数据被丢弃，由当夜批处理结果替换**——使银行长期数据可信要求更易满足，功能上几无损失。

> **小心——最佳安全在于谨慎**。（I.iii.43）

- **安全第一（Safety first）**。在分配资源时——**力求避灾，而非求最优**。多年虚存、网络、磁盘分配、数据库布局等经验已清楚：**通用系统无法做到最优**——**而极易过载并大幅降级**。**任何资源需求超过容量 2/3——除非负载特征很明确，否则系统都难指望表现良好**。**幸而硬件便宜且日趋便宜**——可承担"过量容量"——内存尤其便宜——而**充足内存能让 CPU/带宽等其他资源被更充分使用**。
   关于优化的悲哀真相，第一批分页系统就教过我们——**当年内存极贵，人们幻想靠精巧的调换策略"挤出每一字节"**——把相关过程放同页、由先前引用预测下一页、让共享数据/代码的作业拼跑——**没人学会怎么做**——**最终是内存便宜了，系统拿它做缓冲让简单按需分页能用**。**唯一重要的是避免抖动——避免对可用内存需求过度**。
   "聪明"奏效的系统都是**载荷很可知**的——比如 360/50 APL [4] 给每用户同样大小工作区、所有用户共用同样系统代码——使系统代码常驻、为每用户分配连续盘段、把"换出/换入"与每单位计算重叠——**很好用**。

> **Alto 最棒之处是它夜里也不跑得更快**。（J. Morris）

类似教训也适用于 CPU 时间——**交互使用的响应时间重要**（人在等）——许多按计算优先级、工作集大小、内存载荷、历史、I/O 概率调度的尝试都失败——**只有最粗糙的参数有可理解的效果**：交互/非交互、高/前台/后台优先级。**最成功的方案是"给每个作业一份固定份额，不超 100%"**——空闲周期被浪费或（运气好）被后台作业吃掉。**自然延伸是个人计算机**——**每用户至少一台 CPU**。

> **每人之耳听之，少与之口；接纳每人之责难，但保留你的判断**。

- **卸载以控制需求（Shed load）**——是上一条的推论。**有许多卸载方式**：交互系统拒新用户、甚至拒在用用户；内存管理器限制作业，使其工作集都装得下；网络丢包；最坏时让系统崩溃后更谨慎重启。**Bob Morris 提议过：分时系统每终端装个红按钮**——用户对服务不满就按——系统须改善服务或踢他下线——**长期来看做出公平选择**——**避免让人在无法提供有用服务的终端前浪费时间**。
   Arpanet 最初规约 [32] 说**网络一旦接受包就保证递送**——除非接收机宕或网络节点持包时失败——**这是个糟主意**——使最坏情形下避死锁很难——遵守它带来许多复杂与低效——**而客户并未受益**（仍要处理由主机/网络失败丢失的包）（参见 §4 端到端）——**最终被放弃**。**Pup 互联网 [3]** 面对更多变运输条件——**自始就在一遇拥塞便果断丢包**。

## 4. 容错

> **可靠性不可避免之代价是简洁**。（C. Hoare）

**让系统可靠不算很难——若你知道怎么入手——但向已有设计追加可靠性极困难**。

> **此为重中之重——/ 对自己真——/ 那必如夜随昼——/ 你便不能对任何人虚伪**。

- **端到端（End-to-end）**——**应用层的错误恢复对一个可靠系统绝对必要——其他错误检测/恢复在逻辑上不必要——只为性能**。最早由 Saltzer [46] 指出，应用面甚广。
   例：从机器 A 上盘的文件系统传到机器 B 上盘的文件系统——**要相信正确比特真的在 B 盘上**——必须从 B 盘读、算合理长度（如 64 比特）的校验和、与 A 盘比特的校验和匹配——**核验"A 盘到 A 内存、A 经网到 B、B 内存到 B 盘"任一段都不够**——可能在别处出错、内存中比特被破坏等。**这些中间核验也并非必要**——若端到端核验失败，全部传输可重做。**当然这费功夫——若错误频繁——中间核验能减少"必须重做的工作量"**——但这是性能问题，不影响"文件传输的可靠性"。**剑桥环网中惯于以"仅端到端核验"复制 58 MB 整盘——错很罕见、20 分钟工作很少需要重做** [36]。
   许多 hint 使用都是这一思想的应用。Pup 互联网 [4] 在多层采取端到端策略——网络主要服务是把数据包从源传到目的——包可能穿越错误率/属性极不同的多个网络——存转发节点空间不足时被迫丢包——最佳路由仅有粗略估计，且部分网络失败/恢复时可能极错——**在这些不确定下，Pup 仅"尽力而为"递送即给客户提供良好服务**——包可能丢且不通知发送方、传输中可能损坏——客户必须自己提供错误控制处理这些（更高层 Pup 协议提供如可靠字节流之复杂服务）——**而包传输也尝试把问题报告给客户**（适度错误控制——16 位校验和、可能时通知发送方"已被丢弃"）——**这些都是"尽力而为"——不大让实现复杂**。
   端到端策略两大问题：(1) 它需"成功 / 失败"的廉价测试；(2) 在系统投产承重负载之前看不见的严重性能缺陷。

> **记得你？是的——/ 我会从我记忆之卷上——/ 抹去一切轻浮可爱的记录、—— / 一切书中之言、形式与压力、—— / 那些被青春与观察抄写于此者；—— / 你的命令将独活于—— / 我大脑之书与卷之内——不掺杂物**。（I.v.97）

- **以日志记录"对象状态的真相"（Log updates to record the truth）**——日志是非常简单的数据结构，可被可靠地读写，并可廉价地强制刷到盘或其他能从崩溃中存活的稳定存储——**因只追加，写量最少；任何崩溃时刻日志的有效性都易保证**；复制日志、写到磁带等都方便而廉价。**多年来日志被用于保证数据库不丢信息** [17]——**此思想颇通用，可用于普通文件系统** [35, 49] **及许多不那么显然的情境**。**当日志持有 truth 时，对象当前状态非常像 hint**（不完全是 hint——因没有廉价的校验法）。
   用法：**记每次更新为日志条目**——含更新过程名与其参数——过程必须**函数式**（同参数总有同效果）：参数之外无任何影响过程的状态——**意味着该日志条目稍后可被重执行**——若被更新对象处于"首次更新时的状态"——重执行后会到达"首次更新后的状态"。归纳：**对相同的对象重执行一序列日志条目——产出相同对象**。
   两条要求：
   1. **更新过程必须是真正函数**：结果不依赖参数外状态；除其所属日志的对象外无副作用；
   2. **参数必须是值之一**：立即值（整型、字符串等——可以很大、像数组或表，但完整值须复制进日志条目）；对**不可变对象**的引用。
   多数对象当然非不可变——**特定版本则不可变**——更新改变版本。**用对引用一对 [对象标识, 更新次数] 无歧义地引用对象版本**——若对象标识引到该对象的日志，重放指定次数日志条目即可得该版本——重放时可能要找别的对象版本——**只要每次更新只引"现存版本"——便无环——过程会终止**。
   例：Bravo 编辑文档恰有两个更新函数：

```
Replace(old: Interval, new: Interval)
ChangeProperties(where: Interval, what: FormattingOp)
```

`Interval` 是 [文档版本, 首字符, 末字符]；`FormattingOp` 是从属性到属性的函数（属性如 italic 或 leftMargin；FormattingOp 如 leftMargin := leftMargin + 10、italic := true）——**所有编辑命令都化简为这两个函数的应用**。

> **当心——/ 莫卷入争吵——但既已陷入——/ 让对手当心你**。

- **让动作原子或可重启（Make actions atomic or restartable）**——**原子动作（事务）要么完成、要么无效果**。多数主存系统中取/存一字是原子的。**容错优势显然**：失败时无效果——恢复时不必处理任何中间态 [28]。数据库系统已用日志提供原子性 [17]——基本思想是**给每个原子动作分配唯一标识，用于标记其相关日志条目**；动作的**提交记录** [42] 表示其状态：进行中、已提交（逻辑完成，即便仍有清理）、已中止（逻辑取消，即便仍有清理）——提交记录的状态变化也作为日志条目记下；动作可被提交，仅当其所有更新的日志条目都齐——失败后恢复对每个已提交动作应用其日志条目、对每个已中止动作回滚其更新——**变奏甚多** [54]。
   日志条目通常需**可重启（restartable / idempotent）**——能完整执行前任意次部分执行而不改结果。例：把一组值存入一组变量是可重启的；变量加 1 不是。**可重启日志条目可应用于对象当前状态——无需恢复旧态**。
   此基本方法可用于任何永久存储——**简单情形可用粗糙变体**——前述 Alto 文件系统实质上把磁盘 label 与 leader 当作日志、必要时由其重建别的数据结构——**像多数文件系统，只有文件分配/目录动作是原子的——文件系统不帮客户做更新原子化**。**Juniper 文件系统** [35, 49] 走得远——**让每客户能把任意一组更新作为一个原子动作**——用"shadow pages" 之诀：**把数据页从日志移入文件——只需改 B-tree 中（实现"文件地址 → 盘地址"映射的）指针——此诀首次用于 Cal 系统** [50]。普通文件系统的合作客户也可实现原子动作——**每次访问文件前检查是否需要恢复——必要时按特定命名的日志文件中条目执行** [40]。
   **原子动作一般实现非平凡**——但**远没其公众形象暗示的那么难**。**有时更弱但更廉价的方法即可**。**Grapevine** 邮件传输/注册系统 [1] 在跨国网中数百台机器上维护"名/分发列表"的复制数据库——**更新在某一站点做并通过邮件系统本身传播到别站点**——保证更新最终抵达——但站点失败/恢复、网划分时**到达顺序可能差异巨大**——每条更新带时间戳——**最新者赢**。足够时间后所有站点收到所有更新、达成一致——**传播过程中各站点可能不一致**（如对某人是否为某分发列表成员）——**这种偶发不一致与延迟对该系统的有用性影响不大**。

## 5. 结论

> **大人，最谦卑地告辞**。

这种"良言与轶事的合集"读起来颇令人疲倦——也许小剂量、临睡前最适合服用。略作辩白：**我至少违反过这些规则中的大多数一次——而且几乎总后悔**。文献给出我只素描一笔的系统/技巧的更完整故事——其中许多还有更完整的论证。所有口号汇于本文开头的图 1。
